# バックエンド構成(apps/api)

バックエンド(FastAPI)のフォルダ構成と、コードをどこに書くかのルールをまとめた資料。
新しい機能を作るときは、この資料のルールに従う。

| 項目     | 内容                                                            |
| -------- | --------------------------------------------------------------- |
| 対象     | `apps/api`                                                      |
| 採用     | 機能別(ドメイン別)構成 + 機能の中で router → service → repository の 3 層 |
| 決定日   | 2026-09-28(4.3 の製造中に、4.1・4.2 のコードもこの構成へ移行)  |

---

## 1. なぜ構成のルールが必要?

1 つのファイルに窓口・業務ロジック・SQL を全部書くと、機能が増えるにつれて次の問題が起きる。

- どこに何が書いてあるか分からなくなる
- 1 か所の修正が、思わぬところに影響する
- テストしにくい(SQL を試したいだけなのに、API 全体を動かす必要がある)

大規模な開発現場では、**「機能ごとにフォルダを分ける」** と **「フォルダの中は役割ごとにファイルを分ける」** の 2 つを組み合わせることが多い。jelgram もこの形にする。

## 2. フォルダ構成

```
apps/api/app/
├── main.py              アプリの組み立て(CORS・各機能のルーターの登録)
│
├── core/                全機能が使う共通の土台
│   ├── config.py          設定(.env の読み込み)・SettingsDep
│   └── db.py              DB 接続(エンジン・セッション)・DbSessionDep
│
├── health/              ヘルスチェック
│   ├── router.py          GET /health
│   └── schemas.py         HealthResponse
│
├── auth/                認証
│   ├── router.py          GET /me
│   ├── schemas.py         CurrentUser
│   ├── dependencies.py    JWT 検証・CurrentUserDep(他の機能が「ログイン必須」にするときに使う)
│   └── constants.py       JWT_ALGORITHMS など
│
└── posts/               投稿・いいね
    ├── router.py          窓口(GET/POST /posts など)
    ├── schemas.py         入出力の形(PostCreate・PostResponse など)
    ├── service.py         業務ロジック
    ├── repository.py      DB アクセス(生の SQL)
    ├── exceptions.py      この機能のエラー(PostNotFoundError など)
    └── constants.py       この機能の定数(CONTENT_MAX_LENGTH など)
```

- 機能のフォルダには、**必要なファイルだけを置く**。例えば `health/` は DB を使わないので `service.py`・`repository.py` はない
- 4.5(AI チャット)は `chat/`、4.4(画像アップロード)は `uploads/` のように、機能ごとにフォルダを追加する
- テーブルの定義は `supabase/migrations/` の SQL だけが持つ。Python 側にテーブルの形を写したクラス(ORM モデル)は作らない(8章)

## 3. 各ファイルの役割

| ファイル          | 役割                                                         | 書いてよいもの                                    | 書かないもの                          |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------- | ------------------------------------- |
| `router.py`       | 窓口。リクエストを受け取り、service を呼んで結果を返す       | URL・メソッド・`response_model`・依存関数の受け取り | 業務ロジック・SQL                     |
| `schemas.py`      | API で受け取る・返すデータの形(Pydantic)                  | `BaseModel` を継承したクラス・入力の制約           | DB のテーブル定義                     |
| `service.py`      | 業務ロジック。チェック・確定(commit)・応答の形への詰め替え | 業務ルールの判断・`session.commit()`・例外の raise | SQL(`select` など)                  |
| `repository.py`   | DB アクセス。SQL はここにだけ書く                            | 生の SQL(`select`・`insert`・`delete` など)      | `commit`・HTTP のこと(ステータスなど) |
| `exceptions.py`   | この機能のエラー                                             | `HTTPException` を継承したクラス                   |                                       |
| `constants.py`    | この機能の定数                                               | 文字数の上限・件数など、コードで決める値           | 環境で変えたい値(→ `core/config.py`) |
| `dependencies.py` | 他のファイルから `Depends` で使う部品                        | 依存関数・`〜Dep` の別名                           |                                       |

### Java(Spring)を知っている人向けの対応表

| jelgram           | Spring の場合      |
| ----------------- | ------------------ |
| `router.py`       | Controller         |
| `service.py`      | Service            |
| `repository.py`   | Repository(DAO)。MyBatis の Mapper のように SQL を直接書く |
| `schemas.py`      | DTO(Request / Response) |

## 4. 1 回のリクエストの流れ

`POST /posts/{post_id}/like` の例。

```
リクエスト
   ▼
posts/router.py ……… like_post(post_id, user, session)
   │  依存関数:auth/dependencies.py(ログイン確認)・core/db.py(DB セッション)
   ▼
posts/service.py ……… like_post(session, post_id, user_id)
   │  ① 投稿があるか確かめる → なければ PostNotFoundError(404)
   │  ② repository にいいねの追加を頼む
   │  ③ session.commit() で確定
   │  ④ いいね数などを repository に聞いて、LikeResponse を作る
   ▼
posts/repository.py …… insert_like / count_likes / is_liked
   │  生の SQL を実行する
   ▼
PostgreSQL(Supabase)
```

## 5. 依存の向きのルール

矢印は「読み込む(import する)」の向き。**逆向きの import はしない。**

```
main.py
   ▼
<機能>/router.py
   ▼
<機能>/service.py
   ▼
<機能>/repository.py

どの層からも使ってよいもの:<機能>/schemas.py・constants.py・exceptions.py、core/
```

| ルール                                                    | 理由                                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| repository から service や router を import しない         | 下の層が上の層を知ると、1 か所の変更が全体に広がる                                      |
| 他の機能のものを使うときは、その機能の公開部品だけを使う  | 例:`posts` は `auth/dependencies.py` の `CurrentUserDep` を使う。`auth` の内部の関数(`_unauthorized` など)は使わない |
| `core/` は機能のフォルダを import しない                  | `core/` はすべての機能の土台なので、特定の機能に依存させない                            |

## 6. 置き場所の決め方(迷ったとき)

| 迷うもの                         | 置き場所                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------- |
| 定数                             | 使う機能の `constants.py`。環境(開発・本番)で変えたい値は `core/config.py`  |
| 入出力の形                       | 使う機能の `schemas.py`。他の機能でも使うなら、元の機能の `schemas.py` から import する |
| DB のテーブル                    | 定義は `supabase/migrations/`。読み書きする SQL は、使う機能の `repository.py`(他の機能のテーブルも JOIN してよい) |
| 業務のエラー                     | 使う機能の `exceptions.py`                                                       |
| 複数の機能で共通の仕組み         | `core/`(設定・DB 接続など、業務に関係ない土台だけ)                            |

## 7. トランザクション(確定)のルール

- **確定(`session.commit()`)は service だけが行う**
- repository は SQL を実行するだけで、確定しない。DB が振った id が必要なときは、SQL に `returning id` を付けて受け取る(確定はしない)
- 理由:1 つの業務処理で複数の repository の関数を呼ぶとき、途中で失敗したら全部を取り消したい。確定のタイミングを service 1 か所に集めると、それができる

## 8. SQL の書き方

SQL は ORM を使わず、**生の SQL** を `repository.py` に書く。

- `text("select ... where id = :post_id")` で包み、`session.execute(sql, {"post_id": post_id})` で実行する
- 値は **必ずバインド変数**(`:名前`)で渡す。f-string や `+` で値を SQL に埋め込まない(SQL インジェクションになる)
- キーワードは小文字(`supabase/migrations/` と揃える)。テーブルには短い別名(`posts p` など)を付ける
- 列名のタイプミスは実行するまで分からないので、repository のすべての SQL をテスト(本物の DB)で 1 回は実行する

## 9. テストの置き場所

```
apps/api/tests/
├── conftest.py      共通の準備(テスト用の設定・DB のロールバック・テスト用ユーザー)
├── test_config.py   core/config.py
├── test_health.py   health/
├── test_auth.py     auth/
└── test_posts.py    posts/(API を通して、router → service → repository をまとめて確かめる)
```

- テストファイルは機能ごとに 1 つ(`test_<機能>.py`)。テストが増えて 1 ファイルが大きくなったら、`tests/<機能>/` のフォルダに分ける

## 10. 新しい機能を追加するときの手順

1. `app/<機能>/` フォルダと空の `__init__.py` を作る
2. 必要なファイルを、`repository.py` → `schemas.py` → `service.py` → `router.py` の順に作る(下の層から作ると、1 つずつ動作を確かめられる)
3. `main.py` に `from app.<機能>.router import router as <機能>_router` と `app.include_router(<機能>_router)` を追加する
4. `tests/test_<機能>.py` を作る
