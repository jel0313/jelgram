## 1. この機能で作るもの

### 💡 なぜ必要?

jelgram の中心は **タイムライン**。投稿を並べて表示し、書き込み、いいねを付けられることが、SNS としての最低限の機能になる(要件定義書 3.2)。
4.2 までの API は DB を使っていなかった。4.3 で初めて **DB(Supabase の PostgreSQL)につないでデータを読み書きする** ので、DB 接続の土台もここで作る。4.5 の AI チャット(会話履歴の保存)も、この土台を使う。

### 全体の中での位置づけ

★ が今回(4.3)作るもの。

```
ブラウザ
   │ Authorization: Bearer <JWT>
   ▼
FastAPI
   ├─ get_current_user(4.2)…… 誰からのリクエストか
   │
   ├─ ★ GET    /posts ……………… タイムライン(新しい順)
   ├─ ★ POST   /posts ……………… 投稿する
   ├─ ★ POST   /posts/{id}/like … いいねする
   ├─ ★ DELETE /posts/{id}/like … いいねを取り消す
   │      │
   │      └→ ★ router → service → repository(posts/)
   │             └→ ★ DB セッション(core/db.py)
   │                    │
   │                    ▼ 生の SQL(repository.py に書いたもの)
   │             Supabase PostgreSQL(Session プーラー経由)
   │               profiles / posts / likes(3.2 で作成済み)
   │
   └─ /chat など(4.5 で同じ DB セッションを使う)
```

| 作るもの              | ひとことで言うと                                                         |
| --------------------- | ------------------------------------------------------------------------ |
| DB 接続(`core/db.py`) | DB への接続を管理し、リクエストごとに「DB との会話の窓口」を渡す       |
| 投稿・いいね(`posts/`) | タイムラインの取得・投稿・いいね・いいね取り消し。router・service・repository の 3 層に分け、SQL は repository に **生で** 書く |
| テストの土台          | 本物の DB でテストし、終わったら全部取り消す仕組み                       |

### 用語集

| 用語                     | 意味                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------- |
| SQLAlchemy               | Python から DB を操作するためのライブラリ。今回は **接続の管理と、生の SQL の実行** に使う              |
| psycopg                  | Python と PostgreSQL の間で実際に通信するライブラリ(ドライバー)。SQLAlchemy が内部で使う             |
| 生の SQL                 | SQL を文字列のまま書くこと。SQLAlchemy では `text("select ...")` で包んで実行する                        |
| バインド変数             | SQL の中の `:post_id` のような「値の差し込み口」。値は SQL とは別に渡すので、SQL インジェクションを防げる |
| ORM                      | Object-Relational Mapping。テーブルの1行を Python のオブジェクトとして扱い、SQL を自動で作るしくみ。**今回は使わない**(6.3) |
| エンジン                 | DB への接続をまとめて管理する SQLAlchemy の部品。アプリに1つだけ作る                                    |
| セッション               | DB との1回分の「会話」。この中で読み書きし、最後に確定(コミット)する                                  |
| トランザクション         | 「全部成功したら確定、途中で失敗したら全部なかったことにする」処理のまとまり                              |
| コミット・ロールバック   | コミット = 変更を確定する。ロールバック = 変更をなかったことにする                                     |
| コネクションプール       | DB への接続を使い回すしくみ。接続を毎回作ると遅いので、作った接続をためておいて再利用する                |
| サブクエリ               | SQL の中に入れる、別の小さな SQL(例:「この投稿のいいね数」を数える SQL)                               |
| N+1 問題                 | 一覧を1回取得したあと、各行ごとに追加で SQL を発行してしまい、SQL の回数が「1 + 件数」に増える問題      |
| 冪等(べきとう)         | 同じ操作を何回やっても、結果が1回やったときと同じになる性質                                             |

## 3. DB 接続のしくみ

### 💡 なぜ必要?

DB への接続は「電話をかける」のに似ている。毎回かけ直すと時間がかかるので、**つながった回線をためておいて使い回す**(コネクションプール)。
また、リクエストごとに「どこまで書き込んだら確定するか」をはっきりさせないと、途中で失敗したときに中途半端なデータが残ってしまう。
これらを SQLAlchemy の **エンジン** と **セッション** に任せる。

### 3.1 接続経路

```
【FastAPI が動く場所】
  開発:あなたの Mac(localhost:8000)─┐
  本番:Render ─────────────────────────┤
                                        │ インターネット越しに接続
                                        │ postgresql+psycopg://…@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres
                                        ▼
【Supabase(別のサービス・東京リージョン)】
  Session プーラー …… 接続の受付窓口。IPv4 で接続できる(Render の無料プランは IPv4 のみ)
     ▼
  PostgreSQL 17(profiles / posts / likes / chat_messages)
```

- DB は Render の中ではなく、Supabase にある。Render は「処理をする場所」、Supabase は「データを保管する場所」。Render の無料サーバーは再起動のたびに中身がリセットされるので、データを置けない
- 開発でも本番でも、FastAPI はインターネット越しに Supabase の DB へ接続する。変わるのは FastAPI の置き場所と、接続先(開発用 / 本番用の Supabase プロジェクト)だけ

- `.env` の `DATABASE_URL` は `postgresql://` で始まる(Supabase の管理画面の表示どおり)。SQLAlchemy は `postgresql://` だと別のドライバー(psycopg2)を使おうとするので、**プログラムの中で `postgresql+psycopg://` に置き換えて** 使う
- FastAPI はテーブル所有者の `postgres` ユーザーで接続するので、RLS(3.2 で設定)の影響を受けない。「自分のデータだけ」などの制御は、API のコードで行う

### 3.2 エンジンとセッション

```
アプリ起動後、最初に DB を使うとき
   get_engine() …… エンジンを1つ作る(コネクションプールを持つ)
                     2回目以降は同じものを返す(キャッシュ)

リクエストが来るたび
   get_db()
     ├ Session(engine) を作る …… プールから接続を1本借りる
     ├ yield session …………………… エンドポイントに渡す
     │     ↓
     │   router → service → repository:読み書き → service が session.commit()
     │     ↓
     └ with を抜ける ……………………… セッションを閉じ、接続をプールに返す
                                      (コミットしていない変更は自動で取り消される)
```

- **なぜ `yield` を使うのか?** `yield` の前が「準備」、後が「片付け」になる。エンドポイントでエラーが起きても、片付け(接続を返す)が必ず実行される。FastAPI の公式ドキュメントでも、DB セッションはこの書き方
- **`pool_pre_ping=True` を付ける理由**:Render のスリープや Supabase 側の都合で、ためておいた接続が切れていることがある。借りる前に「まだつながってる?」と軽く確かめて、切れていたら作り直してくれる

> ⚠️ **つまずきポイント**:FastAPI から `create table` などのテーブルを作る・変える SQL は **実行しない**。テーブルは 3.2 の `supabase/migrations/` の SQL で管理している。FastAPI が実行するのは、データを読み書きする SQL(`select`・`insert`・`delete`)だけ。

### posts の中の層の関係

矢印は「使う(import する)」の向き。逆向きには使わない。

```
main.py
   ▼
posts/router.py ……… 窓口。受け取って service を呼ぶだけ
   │  使う:auth/dependencies.py(CurrentUserDep)・core/db.py(DbSessionDep)・core/config.py(SettingsDep)
   ▼
posts/service.py …… 業務ロジック。チェック → repository → commit → 応答の形に詰め替え
   │  使う:posts/schemas.py・posts/exceptions.py・posts/constants.py
   ▼
posts/repository.py … 生の SQL を実行する(commit はしない)
   ▼
PostgreSQL(profiles / posts / likes)
```

- **なぜ 3 層に分けるのか?** 窓口(HTTP のこと)・業務ルール・SQL を分けると、それぞれを単独で読める・直せるようになる。例えば「タイムラインの並び順を変える」なら `repository.py` だけ、「本文の上限を変える」なら `constants.py` だけを直せばよい。大規模な開発現場で一般的な分け方(Java の Controller・Service・Repository と同じ考え方)
- `posts` の SQL は `profiles` テーブルも読む(投稿者の名前)。テーブルの持ち主の機能(`users/`)にファイルを作る必要はなく、SQL の中で JOIN すればよい

## 5. 使用パッケージ

| 種別 | パッケージ         | 用途                                                                        |
| ---- | ------------------ | --------------------------------------------------------------------------- |
| 本体 | `sqlalchemy`       | エンジン(コネクションプール)・セッション(トランザクション)・生の SQL の実行(`text()`)。ORM は使わない |
| 本体 | `psycopg[binary]`  | PostgreSQL と通信するドライバー(psycopg 3)                               |

- `[binary]` を付けると、PostgreSQL のクライアントライブラリ(libpq)を別途インストールしなくても動く。Render でもそのまま使える
- 2026-09-28 時点の最新は SQLAlchemy 2.1.1、psycopg 3.3.6

> ⚠️ **つまずきポイント**:ネットで調べると `psycopg2` を使う記事が多いが、これは古い世代(psycopg 2)。今回は `psycopg`(3)を使う。接続文字列の `+psycopg` もこれに対応している。

## 6. モジュール設計

### 6.1 `app/core/config.py`:追加分

| 名前                      | 種類       | 戻り値 | 仕様                                                                                             |
| ------------------------- | ---------- | ------ | ------------------------------------------------------------------------------------------------ |
| `sqlalchemy_database_url` | プロパティ | `str`  | `database_url` の先頭の `postgresql://` を `postgresql+psycopg://` に置き換えて返す(先頭の1回だけ) |

例:`postgresql://u:p@host:5432/postgres` → `postgresql+psycopg://u:p@host:5432/postgres`

- **なぜ `.env` の値を直接書き換えないのか?** Supabase の管理画面からコピーした形のまま貼れるほうが、本番の設定(7.3 の Render)で間違えにくい

### 6.2 `app/core/db.py`:DB 接続

#### 構成

| 名前             | 種類             | 仕様                                                                                          |
| ---------------- | ---------------- | --------------------------------------------------------------------------------------------- |
| `get_engine()`   | 関数(キャッシュ) | `create_engine(settings.sqlalchemy_database_url, pool_pre_ping=True)` を1回だけ作って返す     |
| `get_db()`       | 依存関数         | `Session(get_engine())` を `with` で作り、`yield` で渡す                                      |
| `DbSessionDep`   | 型の別名         | `Annotated[Session, Depends(get_db)]`。各エンドポイントの引数に使う                           |

- **なぜ生の SQL なのにセッションを使うのか?** セッションは「トランザクションの管理役」として使う。service の `session.commit()` で確定する、テストで全部ロールバックする(8.1)、といった仕組みは、SQL を生で書いても同じように使える
- **なぜエンジンをファイルの先頭で作らず、関数 + キャッシュにするのか?** 4.2 の `get_jwks_client()` と同じ理由。`import` しただけで DB 接続の準備が始まらないようにし、テストで差し替えやすくする

#### 🔧 実装のヒント

| やりたいこと           | 使うもの                                                                        |
| ---------------------- | ------------------------------------------------------------------------------- |
| エンジンを作る         | `from sqlalchemy import create_engine`、`from sqlalchemy.engine import Engine` |
| セッションを作る       | `from sqlalchemy.orm import Session`。`with Session(engine) as session:`        |
| `yield` する依存関数   | 戻り値の型は `collections.abc.Iterator[Session]`                                |

### 6.3 SQL の書き方(生の SQL)

#### 💡 なぜ生の SQL で書くのか?

SQLAlchemy には、SQL を Python の書き方で組み立てる機能(ORM など)もある。今回はそれを使わず、**SQL を文字列のまま書く**。

- **実行される SQL がそのまま読める**:レビューのとき、そのまま SQL Editor に貼って試したり、実行計画(`explain`)を見たりできる
- **SQL の知識がそのまま使える**:Python 独自の書き方を覚えなくてよい。Java(MyBatis など)の現場と同じ感覚で書ける
- **テーブルの定義が 1 か所で済む**:テーブルの形は `supabase/migrations/` の SQL だけが持つ。Python 側にモデルクラスを作って二重に管理しなくてよい

代わりに、**列名のタイプミスは実行するまで気づけない**。そのため、repository のすべての SQL を、本物の DB を使うテスト(8章)で必ず 1 回は実行する。

#### 書き方のルール

| ルール                                                     | 例・理由                                                                                         |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| SQL は `repository.py` にだけ書く                          | service・router には書かない([バックエンド構成](../../バックエンド構成.md))                    |
| SQL は `text("...")` で包んで `session.execute()` で実行する | `session.execute(text("select ..."), {"post_id": post_id})`                                     |
| 値は **必ずバインド変数** で渡す                           | `where id = :post_id` と書き、値は辞書で渡す。f-string や `+` で値を SQL に埋め込まない(SQL インジェクションになる) |
| キーワード・関数は小文字で書く                             | `select`・`count(*)` など。`supabase/migrations/` の SQL と揃える                                |
| テーブルには短い別名を付ける                               | `posts p`・`profiles pr`・`likes l`                                                              |
| 列名がぶつかるときは `as` で別名を付ける                   | `posts.id` と `profiles.id` は両方 `id` なので、投稿者の列は `pr.id as author_id` のように `author_` を付ける |
| 共通の SELECT を使い回すときは、固定の文字列だけをつなげる | `_SELECT_POSTS + "where p.id = :post_id"`。つなげてよいのはコードに書いた固定の文字列だけ。値はつなげない |

#### テーブル定義(参照)

3.2 のマイグレーション(`supabase/migrations/20260928000000_initial_schema.sql`)が正。SQL を書くときは、ここの列名を使う。

| テーブル   | 列             | DB の型       | Python で受け取る型 | 備考                                           |
| ---------- | -------------- | ------------- | ------------------- | ---------------------------------------------- |
| `profiles` | `id`           | `uuid`        | `UUID`              | 主キー                                         |
|            | `display_name` | `text`        | `str`               |                                                |
|            | `avatar_url`   | `text`(NULL 可) | `str \| None`    |                                                |
|            | `created_at`   | `timestamptz` | `datetime`          | 初期値 `now()`                                 |
| `posts`    | `id`           | `bigint`      | `int`               | 主キー。DB が自動で番号を振る(identity)       |
|            | `user_id`      | `uuid`        | `UUID`              | `profiles.id` への外部キー                     |
|            | `content`      | `text`        | `str`               | 空文字は不可(check 制約)                     |
|            | `image_url`    | `text`(NULL 可) | `str \| None`    |                                                |
|            | `created_at`   | `timestamptz` | `datetime`          | 初期値 `now()`                                 |
| `likes`    | `user_id`      | `uuid`        | `UUID`              | 主キー(複合)。`profiles.id` への外部キー     |
|            | `post_id`      | `bigint`      | `int`               | 主キー(複合)。`posts.id` への外部キー        |
|            | `created_at`   | `timestamptz` | `datetime`          | 初期値 `now()`                                 |

- 「Python で受け取る型」は、psycopg が自動で変換してくれる型。`timestamptz` はタイムゾーン付きの `datetime`(UTC)になる
- `likes` の主キーが `(user_id, post_id)` の組なので、同じ人が同じ投稿に 2 回いいねすることは DB が防ぐ

#### 🔧 実装のヒント

| やりたいこと              | 使うもの                                                                         |
| ------------------------- | -------------------------------------------------------------------------------- |
| 生の SQL を書く           | `from sqlalchemy import text` → `text("select ... where id = :post_id")`         |
| 実行して全行を取る        | `session.execute(sql, {"post_id": post_id}).all()`。1 行だけなら `.one()`        |
| 値を 1 つだけ取る         | `session.execute(sql, {...}).scalar_one()`(件数・`exists`・`returning id` など) |
| 行から列を取り出す        | `row.author_id` のように、列名(`as` の別名)で取り出せる                        |

> ⚠️ **つまずきポイント**:バインド変数に PostgreSQL の型変換 `::` を付けて `:name::text` と書くと、`:name` が **バインド変数として認識されない**(値が差し込まれず、SQL のエラーになる)。型変換は `cast(:name as text)` と書く。

### 6.4 `app/posts/`:投稿・いいねの機能

#### 💡 なぜ必要?

タイムラインの画面(5.3)が使う API。画面が1回の呼び出しで表示に必要な情報をそろえられるように、**投稿者の名前・アイコン、いいね数、自分がいいね済みか** までまとめて返す。

#### ファイルごとの役割

| ファイル        | 役割                                                                 | 主な中身                                                                 |
| --------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `constants.py`  | この機能の定数                                                       | `CONTENT_MAX_LENGTH`・`TIMELINE_LIMIT`                                   |
| `schemas.py`    | 入出力の形                                                           | `AuthorResponse`・`PostResponse`・`PostCreate`・`LikeResponse`           |
| `exceptions.py` | この機能のエラー                                                     | `PostNotFoundError`(404)・`InvalidImageUrlError`(422)                 |
| `repository.py` | DB アクセス。SQL はここにだけ書く。commit はしない                   | `find_timeline`・`insert_like` など(6.4.3)                            |
| `service.py`    | 業務ロジック。チェック・commit・応答の形への詰め替え                 | `get_timeline`・`create_post`・`like_post`・`unlike_post`(6.4.4)      |
| `router.py`     | 窓口。受け取って service を呼ぶだけ                                  | 4 つのエンドポイント(6.4.5)                                            |

| `CONTENT_MAX_LENGTH`  | `500` | 本文の最大文字数(要件定義書に追記する)                           |

- **なぜ本文に上限を付けるのか?** 上限がないと、巨大な文章を送られたときに DB 容量(無料枠 500MB)と AI チャットの入力(4.5 で投稿を AI に渡す)を圧迫する
- **なぜ一覧に上限を付けるのか?** 投稿が増えるほど応答が重くなるため。ページングを作るまでの仮の上限
- **なぜ API の形(`PostResponse`)と DB のテーブルの形を分けるのか?** 一致しないから。`PostResponse` には DB の `posts` にない `author`・`like_count`・`liked_by_me` が入る。逆に、DB にあっても API では返したくない列もありうる

#### 6.4.2 例外(`exceptions.py`)

| クラス                 | ステータス | `detail`               | 出す場所                                 |
| ---------------------- | ---------- | ---------------------- | ---------------------------------------- |
| `PostNotFoundError`    | `404`      | `投稿が見つかりません` | service(いいね・取り消しで投稿がない)  |
| `InvalidImageUrlError` | `422`      | `画像の URL が不正です` | service(画像 URL が自分のバケットでない) |

- `HTTPException` を継承する。service で `raise` すると、FastAPI がそのままエラーの応答にしてくれる
- **なぜ `HTTPException(404, "…")` を直接書かずにクラスを作るのか?** 同じエラーを複数の場所で出すときに、ステータスとメッセージが 1 か所で決まる。テストでも「どのエラーか」が名前で分かる

#### 6.4.3 DB アクセス(`repository.py`)

| 名前                                           | 戻り値        | 仕様                                                                              |
| ---------------------------------------------- | ------------- | --------------------------------------------------------------------------------- |
| `_SELECT_POSTS`                                | (定数)`str` | 投稿・投稿者・いいね数・自分がいいね済みか を 1 回で取る SELECT 文。`where`・`order by` は付けない |
| `find_timeline(session, user_id, limit)`       | `list[Row]`   | `_SELECT_POSTS` に並び順(`created_at` 新しい順 → `id` 大きい順)と件数を足して実行 |
| `find_post_row(session, post_id, user_id)`     | `Row`         | `_SELECT_POSTS` に `where p.id = :post_id` を足して 1 行取る                      |
| `exists_post(session, post_id)`                | `bool`        | 投稿があるか(`select exists (...)`)                                             |
| `insert_post(session, user_id, content, image_url)` | `int`    | 投稿を追加し、DB が振った `id` を返す(`returning id`。確定はしない)            |
| `insert_like(session, post_id, user_id)`       | `None`        | いいねを追加。すでにあれば何もしない(`on conflict (user_id, post_id) do nothing`) |
| `delete_like(session, post_id, user_id)`       | `None`        | いいねを削除。なければ何も起きない                                                |
| `count_likes(session, post_id)`                | `int`         | その投稿のいいね数                                                                |
| `is_liked(session, post_id, user_id)`          | `bool`        | 自分がいいね済みか                                                                |

`_SELECT_POSTS` の SQL(`find_timeline` で足す部分も含む)

```sql
select
    p.id,
    p.content,
    p.image_url,
    p.created_at,
    pr.id           as author_id,
    pr.display_name as author_display_name,
    pr.avatar_url   as author_avatar_url,
    (select count(*) from likes l where l.post_id = p.id) as like_count,   -- サブクエリ
    exists (
        select 1 from likes l where l.post_id = p.id and l.user_id = :user_id
    ) as liked_by_me                                                      -- EXISTS
from posts p
join profiles pr on pr.id = p.user_id
order by p.created_at desc, p.id desc   -- find_timeline で足す
limit :limit                            -- find_timeline で足す
```

- **なぜ 1 回の SQL にまとめるのか?(N+1 問題)** 投稿一覧を取ってから、投稿ごとに「いいね数は?」「自分はいいねした?」と SQL を発行すると、50 件で 1 + 50 × 2 = 101 回の SQL になる。Supabase は東京リージョンでもネットワーク越しなので、1 回数十ミリ秒 × 101 回で数秒かかってしまう
- **なぜ並び順に `id` も入れるのか?** 同じ時刻の投稿があると、DB は並び順を保証しない。表示するたびに順番が入れ替わる、という不具合を防ぐ(テストでは実際に同じ時刻になる。8.1 のつまずきポイント)
- **なぜ投稿者の列に `author_` を付けるのか?** `posts` と `profiles` の両方に `id`・`created_at` がある。別名を付けないと、結果の行で同じ名前の列が 2 つになり、どちらか分からなくなる
- **なぜ `insert_post` は `returning id` なのか?** `id` は DB が振る番号なので、INSERT した後でないと分からない。`returning id` を付けると、INSERT と同時にその番号を返してくれる(確定はしない。確定は service の役目。[バックエンド構成](../../バックエンド構成.md) 7章)
- **なぜ `on conflict` に列を書くのか?** `(user_id, post_id)` を書くと、「主キーが重なったときだけ何もしない」になる。書かないと、他の制約の違反まで黙って無視してしまう

#### 6.4.4 業務ロジック(`service.py`)

| 関数                                             | 戻り値               | 仕様                                     |
| ------------------------------------------------ | -------------------- | ---------------------------------------- |
| `get_timeline(session, user_id)`                 | `list[PostResponse]` | タイムライン(最大 `TIMELINE_LIMIT` 件)  |
| `create_post(session, user_id, body, settings)`  | `PostResponse`       | 投稿する                                 |
| `like_post(session, post_id, user_id)`           | `LikeResponse`       | いいねする                               |
| `unlike_post(session, post_id, user_id)`         | `LikeResponse`       | いいねを取り消す                         |

内部で使う関数:`_to_post_response(row)`(repository の 1 行を `PostResponse` に詰め替え。`author_` で始まる列を `author` にまとめる)、`_ensure_post_exists(session, post_id)`(なければ `PostNotFoundError`)、`_like_response(session, post_id, user_id)`(操作後の `LikeResponse` を作る)

**`create_post`**

```
① image_url がある場合、自分のバケットの URL か確かめる …… NG → InvalidImageUrlError(422)
   ↓
② repository.insert_post(…) …… DB が振った id を受け取る(まだ確定していない)
   ↓
③ session.commit() …… 確定
   ↓
④ repository.find_post_row(…) で、GET と同じ形で取り直して PostResponse にする
```

- ① で許可する URL の先頭:`{supabase_url}/storage/v1/object/public/{supabase_storage_bucket}/`
- **なぜ ① が必要なのか?** 何も確かめないと、どこかのサイトの画像や、悪意のあるページの URL を投稿に埋め込める。画像は自分の Storage に上げたもの(4.4)だけにする
- **なぜ ④ で取り直すのか?** `id`・`created_at` は DB が決める値で、投稿者の名前は `profiles` にある。GET と同じ形で返すと、画面は受け取った投稿をそのままタイムラインの先頭に足せる
- 本文の空白・文字数のチェックは、service ではなく `PostCreate`(schemas)が行う。NG なら router に届く前に FastAPI が 422 を返す

**`like_post` / `unlike_post`**

```
① _ensure_post_exists …… 投稿がない → PostNotFoundError(404)
   ↓
② repository.insert_like(…) / repository.delete_like(…)
   ↓
③ session.commit()
   ↓
④ _like_response …… 操作後のいいね数と、自分がいいね済みかを返す
```

- **なぜ「すでにいいね済み」をエラーにしないのか?(冪等)** 画面でボタンを素早く2回押したり、通信が不安定で同じリクエストが再送されたりすることがある。エラーにすると画面側の処理が複雑になる。「何回押しても、最後はいいね済み」になれば十分
- 「いいね済みの投稿で再度押すと取り消し」(要件定義書 3.2)は、画面側が `liked_by_me` を見て POST と DELETE を呼び分ける
- **自分の投稿にもいいねできる**(要件定義書 3.2)ので、投稿者のチェックはしない
- **なぜ操作後のいいね数を返すのか?** 他の人も同時にいいねしているかもしれないので、画面側で「+1」するより、DB の最新の数を返したほうが正確

#### 6.4.5 窓口(`router.py`)

- `APIRouter(prefix="/posts", tags=["posts"])`。`prefix` を付けると、各エンドポイントのパスは `/posts` の後ろだけを書けばよい(`""` → `/posts`、`"/{post_id}/like"` → `/posts/{post_id}/like`)

| 関数          | メソッド・パス                 | 引数(依存関数)                                     | 呼ぶ service              | 成功時 |
| ------------- | ------------------------------ | ---------------------------------------------------- | ------------------------- | ------ |
| `list_posts`  | `GET /posts`                   | `user`・`session`                                    | `service.get_timeline`    | `200`  |
| `create_post` | `POST /posts`                  | `body: PostCreate`・`user`・`session`・`settings`    | `service.create_post`     | `201`  |
| `like_post`   | `POST /posts/{post_id}/like`   | `post_id: int`・`user`・`session`                    | `service.like_post`       | `200`  |
| `unlike_post` | `DELETE /posts/{post_id}/like` | `post_id: int`・`user`・`session`                    | `service.unlike_post`     | `200`  |

- `user: CurrentUserDep`・`session: DbSessionDep`・`settings: SettingsDep` で受け取る
- router には業務ロジックも SQL も書かない。受け取ったものを service に渡して、戻り値をそのまま返す

#### 🔧 実装のヒント

| やりたいこと                           | 使うもの                                                                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 前後の空白を除いて文字数チェック       | `content: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=CONTENT_MAX_LENGTH)]`(`pydantic`) |
| 生の SQL を書く・実行する              | 6.3 の「実装のヒント」                                                                                                    |
| 長い SQL を書く                        | `"""` で囲んだ複数行の文字列にする。短い SQL は `"..." "..."` のように文字列を並べて改行する(Python がつなげてくれる)    |
| 追加して id を受け取る(確定しない)   | SQL の末尾に `returning id` → `session.execute(sql, {...}).scalar_one()`                                                  |
| 「すでにあれば何もしない」INSERT       | SQL の末尾に `on conflict (user_id, post_id) do nothing`                                                                  |
| 行を応答の形に詰め替える               | `row.id`・`row.author_display_name` のように列名で取り出し、`PostResponse(...)` に入れる                                  |
| 確定する                               | service で `session.commit()`                                                                                             |
| service から repository を使う         | `from app.posts import repository` → `repository.find_timeline(...)` のように、モジュール名を付けて呼ぶ(どの層の関数か一目で分かる) |
| 業務のエラー                           | `HTTPException` を継承したクラスを作り、`super().__init__(status_code=404, detail="…")`                                   |
| 応答のステータスを 201 にする          | `@router.post("", response_model=PostResponse, status_code=201)`                                                          |
| パスの `{post_id}` を受け取る          | 関数の引数に `post_id: int`。数字以外が来たら FastAPI が自動で 422 にする                                                 |

- router・service・repository の関数は、すべて `async def` ではなく `def` で書く(psycopg の通信はブロックするため。4.2 の `get_current_user` と同じ理由)

> ⚠️ **つまずきポイント**:SQL に値を入れるときに、`f"... where id = {post_id}"` のように **f-string で埋め込まない**。必ず `:post_id` と書いて、値は辞書で渡す。f-string で埋め込むと、利用者が送った文字列がそのまま SQL として実行される(SQL インジェクション)。

## 8. テスト設計(pytest)

### 💡 なぜ必要?

投稿・いいねは、SQL の書き方1つで「いいね数がずれる」「他人のいいねが自分のものに見える」といった不具合が起きやすい。本物の PostgreSQL で SQL が正しく動くことを確かめる。

### 8.1 テストの仕組み:本物の DB で試して、最後に全部取り消す

偽物の DB(SQLite など)を使うと、PostgreSQL 専用の機能(`on_conflict_do_nothing` など)が動かず、本物との違いで不具合を見逃す。Docker でローカルに PostgreSQL を立てる方法もあるが、この プロジェクトでは Docker を使わない(要件定義書 7.3)。
そこで **開発用の Supabase の DB を使い、テストごとにトランザクションを始めて、最後にロールバックする**。テスト中に作ったユーザー・投稿・いいねは、すべてなかったことになる。

```
テスト1件ごとに
   ① DB に接続し、トランザクションを始める
      ↓
   ② その接続の上でセッションを作る(join_transaction_mode="create_savepoint")
      ↓
   ③ get_db を差し替えて、API がこのセッションを使うようにする
   ④ get_current_user を差し替えて、「テスト用ユーザーとしてログイン中」にする
      ↓
   ⑤ テスト用ユーザーを作る(auth.users に INSERT → トリガーで profiles もできる)
      ↓
   ⑥ client.post("/posts", ...) など …… API の中の commit は「仮の確定」になる
      ↓
   ⑦ ロールバック …… ⑤⑥ で作ったものが全部消える
```

- **`join_transaction_mode="create_savepoint"`**:API の中で `session.commit()` を呼んでも、本当の確定ではなく「セーブポイント(途中の区切り)」の確定になる。外側のトランザクション(①)をロールバックすれば全部消える
- **認証の差し替え**:JWT の検証は 4.2 でテスト済みなので、4.3 では `get_current_user` を「決まったユーザーを返すだけの関数」に差し替える。トークンを作らなくてよいので、テストが短くなる
- テスト用ユーザーは `auth.users` に `id`・`email`・`raw_user_meta_data`(`{"full_name": "表示名"}`)を INSERT して作る。トリガー(3.2)が `profiles` を作るので、表示名も入る
- conftest.py で設定していたダミーの `DATABASE_URL` は削除する。削除すると、`DATABASE_URL` だけは `.env` の本物の値が使われる

fixture の構成(`conftest.py` に追加)

| fixture       | 役割                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------- |
| `db_session`  | ①② と ⑦。トランザクションの中のセッションを渡し、終わったらロールバックする                 |
| `db_client`   | ③。`get_db` を `db_session` に差し替えた TestClient。終わったら差し替えを戻す                 |
| `create_user` | ⑤。表示名を受け取ってテスト用ユーザーを作り、その UUID を返す関数(ファクトリー fixture)     |
| `login_as`    | ④。UUID を受け取って、`get_current_user` がそのユーザーを返すように差し替える関数            |

#### 🔧 実装のヒント

| やりたいこと                        | 使うもの                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 接続してトランザクションを始める    | `connection = get_engine().connect()` → `transaction = connection.begin()`                                  |
| その接続の上でセッション            | `Session(bind=connection, join_transaction_mode="create_savepoint")`                                         |
| 片付け                              | `yield` の後で `session.close()` → `transaction.rollback()` → `connection.close()`                          |
| 生の SQL で INSERT                  | `from sqlalchemy import text` → `session.execute(text("insert into auth.users ... values (:id, ...)"), {"id": ...})` |
| `raw_user_meta_data` に JSON を入れる | SQL の中で `jsonb_build_object('full_name', cast(:name as text))`                                           |
| 差し替えを戻す                      | 4.2 と同じく `yield` の後で `app.dependency_overrides.clear()`                                               |

> ⚠️ **つまずきポイント**:1 つのトランザクションの中では、PostgreSQL の `now()` はずっと同じ時刻を返す。そのため、テストの中で続けて作った投稿は `created_at` がまったく同じになる。並び順に `p.id desc` を入れていないと、T-04 がたまに失敗する(一番見つけにくい種類の不具合)。

> ⚠️ **つまずきポイント**:開発用の DB には、打鍵で作った投稿など **テスト以外のデータも入っている**。`GET /posts` のテストでは、「応答の全体が〇〇と一致する」ではなく、「テストで作った投稿を id で探して、その中身を確かめる」形にする。

- ロールバックしても、投稿の `id` の番号(identity)は元に戻らない。打鍵で作った投稿の `id` が飛び飛びになるが、問題はない
- DB のテストはネットワーク越しなので、4.2 までのテストより遅い(数秒)。開発用の Supabase が一時停止していると失敗する
