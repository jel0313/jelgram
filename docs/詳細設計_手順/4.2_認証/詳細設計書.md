## 1. この機能で作るもの

### 💡 なぜ必要?

jelgram は **全機能ログイン必須**(要件定義書 3.1)。
ログインそのもの(Google ログイン)は Supabase Auth が担当し、ログインに成功したブラウザには **アクセストークン(JWT)** という「通行証」が渡される。

ところが API(FastAPI)には、誰でも curl などで直接リクエストを送れる。4.1 の CORS はブラウザが守るルールなので、API 自体は守れない。
そこで API 側で、リクエストのたびに **「この通行証は本物か? 期限は切れていないか? 誰のものか?」を確かめる** 仕組みを作る。これが JWT 検証。

確かめた結果の「ユーザー ID」は、4.3 以降で「誰の投稿か」「誰のいいねか」「誰の会話履歴か」を決めるのに使う。

### 全体の中での位置づけ

★ が今回(4.2)作るもの。

```
ブラウザ
   │ ① Google ログイン
   ▼
Supabase Auth …… ログインに成功すると JWT を発行(秘密鍵で署名)
   │ ② JWT を受け取る
   ▼
ブラウザ
   │ ③ API を呼ぶ:Authorization: Bearer <JWT>
   ▼
FastAPI
   ├─ CORS チェック(4.1)
   ├─ GET /health …………………… 認証なしで通す(4.1)
   └─ 認証が必要なエンドポイント
         ├→ ★ get_current_user(JWT を検証してユーザーを特定)
         │      └→ Supabase の公開鍵(JWKS)… 取得してキャッシュ
         │
         ├→ ★ GET /me(認証の確認用)
         └→ /posts・/chat など(4.3〜4.6 で同じ仕組みを使う)
```

| 作るもの              | ひとことで言うと                                                                 |
| --------------------- | -------------------------------------------------------------------------------- |
| `get_current_user`    | リクエストの JWT を検証し、ログイン中のユーザー(ID・メール)を返す部品          |
| `GET /me`             | 「今のトークンで、誰としてログインしているか」を返す。認証の動作確認に使う       |
| テスト用の鍵・トークン | 本物の Supabase を使わずに、テストの中で JWT を作って検証できるようにする        |

### 用語集

| 用語               | 意味                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| 認証               | 「あなたは誰か」を確かめること。今回作るもの                                                                |
| 認可               | 「あなたはそれをしてよいか」を決めること(例:会話履歴は自分のものだけ見られる)。4.3 以降の各 API で行う   |
| JWT                | JSON Web Token。ユーザー情報などを JSON で書き、改ざんされていないことを署名で保証した文字列                 |
| クレーム           | JWT の中に書かれている1つ1つの情報(`sub` = ユーザー ID、`exp` = 有効期限 など)                            |
| 署名               | 「発行者が作った本物で、途中で書き換えられていない」ことを証明するデータ                                    |
| 秘密鍵・公開鍵     | ペアになった鍵。秘密鍵で署名し、公開鍵で確かめる。公開鍵は誰に知られても問題ない                            |
| JWKS               | JSON Web Key Set。公開鍵を JSON で公開したもの。Supabase は決まった URL で公開している                      |
| Bearer トークン    | `Authorization: Bearer <トークン>` の形でヘッダーに付けて送るトークン。「持っている人(bearer)を本人とみなす」 |
| 依存関数(Depends) | FastAPI で、エンドポイントの前に共通の処理を実行し、その結果を引数として渡すしくみ                          |

## 3. JWT のしくみ

### 💡 なぜ必要?

コードを書く前に、**JWT の中身と、なぜ検証できるのか** を知っておく。ここが分かっていないと、検証の各項目(期限・`aud`・`iss` など)がなぜ必要なのか分からず、チェック漏れの原因になる。

### 3.1 JWT の形

JWT は `.` で区切られた3つの部分からできている。

```
eyJhbGciOiJFUzI1NiIs...  .  eyJzdWIiOiIxMjM0NTY3...  .  MEUCIQDx3k9...
   ① ヘッダー                  ② ペイロード                 ③ 署名
```

| 部分          | 中身                                                     | 例                                        |
| ------------- | -------------------------------------------------------- | ----------------------------------------- |
| ① ヘッダー    | 署名の方式(`alg`)と、どの鍵で署名したか(`kid`)        | `{"alg": "ES256", "kid": "17f6bc86-..."}` |
| ② ペイロード  | クレーム(ユーザー ID・期限など)                        | `{"sub": "9f1c...", "exp": 1790000000}`   |
| ③ 署名        | ① と ② を Supabase の **秘密鍵** で署名したもの           | (バイナリを文字列にしたもの)            |

> ⚠️ **つまずきポイント**:① と ② は **暗号化されていない**(Base64URL という方式で文字列にしただけ)。誰でも中身を読める。だから JWT にパスワードなどの秘密を入れてはいけないし、「中身が読める = 本物」でもない。本物かどうかは ③ の署名で判断する。

### 3.2 Supabase の JWT に入っているクレーム

| クレーム     | 意味                                          | 今回の使い方                                          |
| ------------ | --------------------------------------------- | ----------------------------------------------------- |
| `sub`        | ユーザー ID(`auth.users.id`、UUID)         | ★ ユーザーの特定に使う。`profiles.id` と同じ値        |
| `email`      | メールアドレス                                | `CurrentUser` に入れる(表示・ログ用)                |
| `exp`        | 有効期限(1970年からの秒数)。発行から1時間  | ★ 期限切れは拒否する                                  |
| `iat`        | 発行日時                                      | 使わない                                              |
| `aud`        | 誰に向けたトークンか。ログイン済みは `authenticated` | ★ `authenticated` 以外は拒否する                  |
| `iss`        | 発行者。`https://<プロジェクトID>.supabase.co/auth/v1` | ★ 自分の Supabase 以外が発行したものは拒否する |
| `role`       | DB のロール(`authenticated`)                | 使わない                                              |
| `session_id` | ログインのセッション ID                        | 使わない                                              |

### 3.3 なぜ API で検証できるのか(公開鍵方式)

```
【発行】Supabase Auth
   ペイロード + 秘密鍵(Supabase だけが持っている)→ 署名を作る
      ↓ JWT
【検証】FastAPI
   JWT のヘッダーの kid を見る
      ↓
   Supabase の JWKS から、その kid の公開鍵を取り出す(誰でも取得できる)
      ↓
   公開鍵で署名を確かめる
      ├ 一致 → ✅ Supabase が発行し、書き換えられていない
      └ 不一致 → ❌ 偽物、または途中で書き換えられている
```

- 開発用の Supabase プロジェクトは **ES256**(楕円曲線を使った公開鍵方式)で署名している(2026-09-28 に JWKS で確認済み)
- 公開鍵は `<SUPABASE_URL>/auth/v1/.well-known/jwks.json` で公開されている。**FastAPI に秘密の値を追加する必要はない**
- 身近なたとえ:Supabase は「ハンコ(秘密鍵)」を持つ役所で、JWT はハンコ付きの証明書。FastAPI は役所が公開している「印影の見本(公開鍵)」と照らし合わせて本物か確かめる

> 📝 **参考**:古い Supabase プロジェクトでは、1つの秘密の文字列(JWT Secret)で署名と検証の両方を行う **HS256** 方式だった。この方式だと FastAPI にも秘密の文字列を置く必要があり、漏れると誰でもトークンを偽造できてしまう。公開鍵方式ならその心配がない。

### 3.4 なぜ Supabase に毎回問い合わせないのか

Supabase には「このトークンは誰のもの?」と問い合わせる API(`/auth/v1/user`)もある。それを使う方法と比べて、今回は **公開鍵で手元で検証する** 方法を選ぶ。

| 方法                       | 速さ                             | ログアウト後のトークン                 |
| -------------------------- | -------------------------------- | -------------------------------------- |
| ★ 公開鍵で手元で検証       | 速い(鍵は最初の1回だけ取得)    | 期限(最大1時間)までは通ってしまう     |
| Supabase に毎回問い合わせ   | リクエストのたびに通信が増えて遅い | すぐに拒否できる                      |

- Render の無料プランはただでさえ遅くなりがちなので、速さを優先する
- ログアウト後もしばらく通るのは、トークンがブラウザから消えるので実害は小さい。個人開発の MVP では許容する

## 5. 使用パッケージ

| 種別 | パッケージ     | 用途                                                                                    |
| ---- | -------------- | --------------------------------------------------------------------------------------- |
| 本体 | `pyjwt[crypto]` | JWT の検証(`jwt.decode`)と JWKS からの公開鍵の取得(`PyJWKClient`)                  |

- `[crypto]` を付けると、ES256 に必要な `cryptography` パッケージも一緒に入る。付け忘れると ES256 のトークンを検証できない
- テストで鍵ペアを作るのにも `cryptography` を使う(追加のインストールは不要)

> ⚠️ **つまずきポイント**:パッケージ名は `pyjwt`、コードで読み込むときの名前は `jwt`(`import jwt`)。PyPI には `jwt` という **別の** パッケージもあるので、`uv add jwt` としないこと。

## 6. モジュール設計

### 6.1 `app/auth.py`:JWT 検証

#### 💡 なぜ必要?

投稿・いいね・チャットなど、これから作る API はすべて「誰からのリクエストか」を知る必要がある。各 API に検証のコードを書くと、同じ処理がいくつも並び、1か所直し忘れただけで穴になる。
そこで検証を **1つの部品(依存関数)** にまとめ、各 API は「この部品を使う」と宣言するだけにする。

```
エンドポイントの関数(user: CurrentUserDep)
      ↑ FastAPI が先に get_current_user を実行し、結果を user に入れて呼ぶ
get_current_user
      ├ 成功 → CurrentUser を返す → エンドポイントの処理へ
      └ 失敗 → HTTPException → エンドポイントは実行されずに 401 / 503 を返す
```

- **なぜミドルウェアではなく依存関数なのか?** ミドルウェアは全リクエストにかかるので、`/health` や `/docs` を除外する処理が必要になる。依存関数なら「使うと宣言した API だけ」に効き、検証結果(ユーザー)をそのまま引数で受け取れる。FastAPI 公式ドキュメントのセキュリティの章もこの方法

#### 構成

| 名前                 | 種類                  | 仕様                                                                                                  |
| -------------------- | --------------------- | ----------------------------------------------------------------------------------------------------- |
| `JWT_ALGORITHMS`     | 定数                  | `["ES256"]`。許可する署名方式                                                                         |
| `JWT_AUDIENCE`       | 定数                  | `"authenticated"`                                                                                     |
| `bearer_scheme`      | 変数                  | `HTTPBearer(auto_error=False)`。ヘッダーからトークンを取り出す。`/docs` の Authorize ボタンも表示される |
| `CurrentUser`        | Pydantic モデル       | ログイン中のユーザー(下の表)                                                                       |
| `get_jwks_client()`  | 関数(キャッシュ)    | JWKS から公開鍵を取得する `PyJWKClient` を作って返す                                                  |
| `get_current_user()` | 依存関数              | JWT を検証して `CurrentUser` を返す(下の「処理の流れ」)                                             |
| `CurrentUserDep`     | 型の別名              | `Annotated[CurrentUser, Depends(get_current_user)]`。各エンドポイントの引数に使う                     |

`CurrentUser` のフィールド

| フィールド | 型            | 元になるクレーム | 備考                                   |
| ---------- | ------------- | ---------------- | -------------------------------------- |
| `id`       | `UUID`        | `sub`            | UUID の形式でなければ無効なトークン扱い |
| `email`    | `str \| None` | `email`          | ない場合は `None`                      |

`get_jwks_client()` の仕様

- URL は `f"{settings.supabase_url}/auth/v1/.well-known/jwks.json"`
- `timeout=5`(秒)を指定する。初期値の 30 秒だと、Supabase につながらないときにリクエストが 30 秒止まってしまう
- `@lru_cache` を付けて、アプリ全体で1つだけ作る。`PyJWKClient` は取得した公開鍵を内部でしばらく(初期値 5 分)覚えているので、1つを使い回さないとキャッシュが効かない

#### 処理の流れ(`get_current_user`)

```
① credentials(bearer_scheme が取り出したもの)が None?
     └ Yes(ヘッダーがない・Bearer 以外)→ 401「認証が必要です」
   ↓
② jwks_client.get_signing_key_from_jwt(トークン)で公開鍵を取り出す
     ├ Supabase につながらない → 503「認証サーバーに接続できません」
     └ トークンが壊れている・該当する鍵がない → 401「トークンが無効です」
   ↓
③ jwt.decode(トークン, 公開鍵, ...)で検証する
     │ 署名 / exp(期限)/ aud / iss / 必須クレームの有無 / alg
     └ どれか1つでも NG → 401「トークンが無効です」
   ↓
④ クレームから CurrentUser を作る(sub → id、email → email)
     └ sub が UUID の形式でない → 401「トークンが無効です」
   ↓
⑤ CurrentUser を返す
```

`jwt.decode` に渡す検証条件

| 引数         | 値                                                  | 理由                                                                                         |
| ------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `algorithms` | `JWT_ALGORITHMS`(`["ES256"]`)                     | トークン側の `alg` を信じない。これを書かないと、署名方式を偽った攻撃が通る余地ができる     |
| `audience`   | `JWT_AUDIENCE`(`"authenticated"`)                 | ログイン済みユーザー向けのトークンだけを通す                                                 |
| `issuer`     | `f"{settings.supabase_url}/auth/v1"`                | 自分の Supabase プロジェクトが発行したものだけを通す(本番用と開発用の取り違えも防げる)     |
| `options`    | `{"require": ["exp", "sub", "aud", "iss"]}`         | クレームが「ない」場合も拒否する。書かないと、`exp` がないトークンは期限チェックが素通りになる |

#### エラー応答

| 状況                                                                    | ステータス | `detail`                         |
| ----------------------------------------------------------------------- | ---------- | -------------------------------- |
| `Authorization` ヘッダーがない・`Bearer` 以外                           | `401`      | `認証が必要です`                 |
| トークンが壊れている・署名が違う・期限切れ・`aud`/`iss` 違い・クレーム不足・`sub` が UUID でない・鍵が見つからない | `401` | `トークンが無効です` |
| JWKS を取得できない(Supabase が停止中・ネットワーク障害)               | `503`      | `認証サーバーに接続できません`   |

- `401` の応答には、必ずヘッダー `WWW-Authenticate: Bearer` を付ける(HTTP の決まりで「Bearer トークンで認証してください」という意味)
- **なぜ無効な理由(期限切れ・署名違いなど)を細かく返さないのか?** 攻撃する側にヒントを与えないため。フロントエンドは「401 ならログイン画面へ」とだけ扱えば十分
- **なぜ Supabase 障害は 401 ではなく 503 なのか?** 401 にすると、フロントエンドが「ログインし直して」と案内してしまい、何度ログインしても直らない。「サーバー側の一時的な問題」と区別する

#### 🔧 実装のヒント

| やりたいこと                        | 使うもの                                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| ヘッダーからトークンを取り出す      | `fastapi.security` の `HTTPBearer`・`HTTPAuthorizationCredentials`。トークン本体は `credentials.credentials` |
| 依存関数の引数に別の依存を受け取る  | `credentials: Annotated[HTTPAuthorizationCredentials \| None, Depends(bearer_scheme)]` のように書く。`get_jwks_client`・`get_settings` も同じように `Depends` で受け取る |
| 公開鍵を取り出す                    | `jwks_client.get_signing_key_from_jwt(token)` の戻り値の `.key`                                            |
| 検証する                            | `jwt.decode(token, key, algorithms=..., audience=..., issuer=..., options=...)`。戻り値はクレームの辞書    |
| 401 / 503 を返す                    | `raise HTTPException(status_code=..., detail=..., headers={"WWW-Authenticate": "Bearer"})`                 |
| `sub` の UUID チェック              | `CurrentUser(id=..., email=...)` を作るときに Pydantic が型を確かめる。失敗すると `pydantic.ValidationError` |

例外の親子関係(`except` で受け取るときに使う)。親を受け取ると、子の例外もまとめて受け取れる。

```
jwt.PyJWTError
 ├ jwt.InvalidTokenError ………………… ③ の失敗はすべてこの子
 │   ├ DecodeError(形式が壊れている)
 │   │   └ InvalidSignatureError(署名が違う)
 │   ├ ExpiredSignatureError(期限切れ)
 │   ├ InvalidAudienceError・InvalidIssuerError
 │   ├ InvalidAlgorithmError(許可していない alg)
 │   └ MissingRequiredClaimError(必須クレームがない)
 └ jwt.PyJWKClientError ………………… ② で鍵が見つからない
     └ PyJWKClientConnectionError(Supabase につながらない)
```

- ② では、**子の `PyJWKClientConnectionError`(503)を先に** `except` する。親の `PyJWKClientError` を先に書くと、つながらない場合も 401 になってしまう
- ② で壊れたトークンを渡すと `DecodeError` が出る(`InvalidTokenError` の子)。② の `except` にも `InvalidTokenError` を含める

> ⚠️ **つまずきポイント**:`get_current_user` は **`async def` ではなく `def`** で書く。`PyJWKClient` は公開鍵を取りに行くとき、処理が終わるまで待つ(ブロックする)通信を使う。`async def` の中でこれを行うと、その間サーバー全体が止まってしまう。`def` で書くと、FastAPI が別のスレッドで実行してくれるので安全。

> ⚠️ **つまずきポイント**:`issuer` は `SUPABASE_URL` から作る。`.env` の `SUPABASE_URL` の末尾に `/` が付いていると `https://xxx.supabase.co//auth/v1` になり、正しいトークンでも全部 401 になる。

### 6.2 `app/routers/me.py`:認証の確認用 API

#### 💡 なぜ必要?

4.2 の時点では、認証が必要な業務 API(投稿など)がまだない。作った認証の部品が本当に動くかを、**テストと打鍵で確かめるための一番小さな API** を用意する。
フロントエンドのログイン処理(5.2)を作るときも、「取得したトークンで API を呼べるか」の確認に使える。

- 要件定義書 9章の API 一覧にはない API なので、要件定義書にも追記する

| 応答モデル             | `@router.get("/me", response_model=CurrentUser)`                         |
| 関数の書き方           | `get_current_user` と同じ理由で `def` で書く(中で待ち時間のある処理はないが、合わせておく) |

## 7. API 仕様

### `GET /me`

```yaml
/me:
  get:
    summary: ログイン中のユーザー情報(認証の確認用)
    tags: [auth]
    security:
      - HTTPBearer: []        # Authorization: Bearer <Supabase のアクセストークン>
    requestBody: なし
    responses:
      "200":

        content:

            schema: CurrentUser    # { id: UUID, email: string | null }

            example:
              detail: トークンが無効です
      "503":
        description: Supabase から公開鍵を取得できない
        content:
          application/json:
            example:

```

- `/health` と `/docs`・`/openapi.json` 以外のすべての API は、引数に `CurrentUserDep` を付ける

## 8. テスト設計(pytest)

### 💡 なぜ必要?

認証は **「通してはいけないものを通さない」** ことが一番大事な機能。正しいトークンが通ることより、偽物・期限切れ・他人向けのトークンを確実に弾くことを重点的にテストする。
打鍵では「期限切れ」や「別の鍵で署名されたトークン」を作るのが難しいので、ここは自動テストで確かめる。

### 8.1 テストの仕組み

本物の Supabase を使うと、テストがネットワークや Supabase の状態に左右される。そこで **テストの中で自分専用の鍵ペアを作り、「Supabase のふり」をする**。

```
conftest.py
   ① テスト用の鍵ペア(ES256)を作る
   ② make_token(...) …… ①の秘密鍵で、クレームを自由に変えた JWT を作る関数
      ↓
test_auth.py
   ③ app.dependency_overrides で get_jwks_client を「偽物の JWKS クライアント」に差し替える
        偽物は、どのトークンに対しても ① の公開鍵を返す
      ↓
   ④ client.get("/me", headers={"Authorization": f"Bearer {make_token(...)}"})
      ↓
get_current_user …… 本物と同じ検証処理が、① の公開鍵で動く
```

- **dependency_overrides**:FastAPI の機能。「この依存関数の代わりに、こっちを使って」と差し替えられる。テストでよく使う
- 偽物の JWKS クライアントは、`get_signing_key_from_jwt(token)` を持ち、`.key` に ① の公開鍵を持つオブジェクトを返せばよい
- テスト用の設定は 4.1 の `conftest.py` のまま(`SUPABASE_URL=https://test.supabase.co`)。なので、正しい `iss` は `https://test.supabase.co/auth/v1`

`make_token` が作る初期のクレーム(引数で上書き・削除できるようにする)

| クレーム | 初期値                               |
| -------- | ------------------------------------ |
| `sub`    | ランダムな UUID(文字列)            |
| `email`  | `test@example.com`                   |
| `aud`    | `authenticated`                      |
| `iss`    | `https://test.supabase.co/auth/v1`   |
| `iat`    | 今                                   |
| `exp`    | 今から 1 時間後                      |
| `role`   | `authenticated`                      |

#### 🔧 実装のヒント

| やりたいこと                  | 使うもの                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| ES256 の鍵ペアを作る          | `from cryptography.hazmat.primitives.asymmetric import ec` → `ec.generate_private_key(ec.SECP256R1())`。公開鍵は `.public_key()` |
| JWT を作る                    | `jwt.encode(クレームの辞書, 秘密鍵, algorithm="ES256", headers={"kid": "test-key"})`                       |
| 今・1時間後                   | `datetime.now(UTC)`、`+ timedelta(hours=1)`。`jwt.encode` は `datetime` をそのまま受け取れる               |
| 関数を返す fixture            | fixture の中で関数を定義して、その関数を `return` する(「ファクトリー fixture」と呼ばれる書き方)          |
| クレームを消せるようにする    | 例:値に `None` を渡されたら、そのクレームを辞書から取り除く                                                |
| `.key` を持つだけのオブジェクト | `types.SimpleNamespace(key=公開鍵)`                                                                       |
| 差し替えて、終わったら戻す    | fixture の中で `app.dependency_overrides[get_jwks_client] = ...` → `yield` → `app.dependency_overrides.clear()` |
| つながらない状態を再現        | 偽物の `get_signing_key_from_jwt` で `jwt.PyJWKClientConnectionError` を `raise` する                      |

> ⚠️ **つまずきポイント**:差し替えを戻し忘れると、後に実行される別のテストにも偽物が残り、「単体だと通るのに、全部まとめて実行すると失敗する」という分かりにくい不具合になる。`yield` の後で必ず `clear()` する。

## 9. 打鍵テスト項目

### 💡 なぜ必要?

自動テストはテスト用の鍵で確かめている。打鍵では **本物の Supabase が発行したトークン** で、実際に通ることを確かめる。ここで初めて「`iss` の URL が本物と一致しているか」「JWKS から鍵を取得できるか」が確認できる。

ログイン画面はまだない(5.2 で作る)ので、Supabase の管理画面で **テスト用のユーザー** を作り、curl でログインしてトークンを取得する。

| No.  | 確認内容                               | 期待結果                                                                      |
| ---- | -------------------------------------- | ----------------------------------------------------------------------------- |
| K-01 | `/docs` に認証の入力欄がある           | 右上に **Authorize** ボタンが出て、`GET /me` に鍵マークが付いている           |
| K-02 | トークンなしで `/me`                   | `401`、`認証が必要です`                                                       |
| K-03 | 本物のトークンで `/me`                 | `200`、`id` が Supabase 管理画面のテストユーザーの User UID と一致する        |
