## 1. この機能で作るもの

### 💡 なぜ必要?

家を建てるときは、いきなり部屋を作らずに、まず基礎と柱を立てる。
この後の 4.2〜4.7 では「ログインの確認」「投稿」「AIチャット」など、たくさんの API を作る。作るたびにプロジェクトの作り方や設定の読み方がバラバラだと、後から直すのが大変になる。
そこで最初に、**すべての API が共通で使う土台(ひな形)** を作る。

### 全体の中での位置づけ

★ が今回(4.1)作るもの。

```
ブラウザ(Next.js / localhost:3000)
   │ HTTP リクエスト
   ▼
FastAPI(apps/api / localhost:8000)
   ├─ ★ CORS チェック(許可されたオリジンだけ通す)
   │      ├→ ★ GET /health
   │      └→ /posts・/chat など(4.2〜4.6)→ Supabase / Gemini(4.3 以降で接続)
   │
   └─ ★ 設定クラス ← .env(起動時に読む)
```

| 作るもの      | ひとことで言うと                                                    |
| ------------- | ------------------------------------------------------------------- |
| 設定クラス    | `.env` に書いた接続先やキーを、プログラムから安全に使えるようにする |
| CORS 設定     | ブラウザ(フロントエンド)から API を呼べるように許可を出す         |
| `GET /health` | 「API が動いているか」を確認するための、一番シンプルな API          |
| テストの土台  | pytest で API を自動テストできるようにする                          |

### 用語集

| 用語           | 意味                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| FastAPI        | Python で API を作るためのフレームワーク                                      |
| エンドポイント | API の窓口になる「URL + メソッド」の組み合わせ(例:`GET /health`)           |
| ルーター       | エンドポイントを機能ごとにまとめるしくみ(`APIRouter`)                       |
| ミドルウェア   | すべてのリクエストの前後に、共通の処理を挟むしくみ(CORS はこれで実現する)   |
| 環境変数       | プログラムの外から渡す設定値。パスワードなどをコードに直接書かないために使う  |
| オリジン       | 「プロトコル + ドメイン + ポート」の組み合わせ(例:`http://localhost:3000`) |
| fixture        | pytest で、テストの前準備を共通化するしくみ                                   |

## 3. ディレクトリ構成

### 💡 なぜ必要?

1つのファイルに全部書くと、API が増えたときに数千行になって読めなくなる。
**「設定」「API の窓口」「アプリの組み立て」「テスト」を別々のファイルに分ける** ことで、どこに何があるかすぐ分かり、修正したときの影響範囲も小さくできる。

> 📐 構成のルール(機能別のフォルダ・各ファイルの役割)は [バックエンド構成](../../バックエンド構成.md) にまとめている。4.1 はその「土台」の部分を作る。

```
apps/api/
├── .env                  ローカル用の環境変数(コミットしない)
├── .env.example          環境変数のひな形(作成済み)
├── .python-version       3.13(作成済み)
├── pyproject.toml        依存パッケージ・pytest・Ruff の設定
├── uv.lock               依存パッケージのバージョン固定(自動生成・コミットする)
├── app/
│   ├── __init__.py       空ファイル
│   ├── main.py           アプリの組み立て(CORS・ルーターの登録)
│   ├── core/             全機能が使う共通の土台
│   │   ├── __init__.py   空ファイル
│   │   └── config.py     設定クラス(環境変数の読み込み)
│   └── health/           ヘルスチェックの機能
│       ├── __init__.py   空ファイル
│       ├── router.py     GET /health
│       └── schemas.py    HealthResponse(応答の形)
└── tests/
    ├── conftest.py       テスト共通の準備(テスト用の環境変数・TestClient)
    ├── test_health.py    ヘルスチェック・CORS のテスト
    └── test_config.py    設定クラスのテスト
```

### ファイル同士の関係

矢印は「使う」の向き。

```
【アプリ】
main.py(組み立て役)
   ├→ core/config.py ............ 設定を読む
   ├→ health/router.py .......... ルーターを登録
   │     └→ health/schemas.py ... 応答の形
   └→ posts/router.py など ...... 4.3 以降、機能ごとのフォルダを同じように追加

【テスト】
conftest.py    → main.py .......... アプリを読み込む
test_health.py → conftest.py ...... client を使う
test_config.py → core/config.py ... 直接テストする
```

- `__init__.py` は「このフォルダは Python のパッケージです」という目印。これがあるので `from app.core.config import get_settings` のように読み込める
- 新しい機能は、`app/<機能>/` フォルダを足して `main.py` に登録するだけで追加できる

## 4. 使用パッケージ

### 💡 なぜ必要?

Python の標準機能だけでも Web サーバーは作れるが、入力チェックやドキュメント生成などを全部自分で書くのは大変。実績のあるパッケージを組み合わせて、**自分は「アプリ固有の処理」だけを書けばいい状態** にする。

| 種別     | パッケージ          | 用途                                                                                  |
| -------- | ------------------- | ------------------------------------------------------------------------------------- |
| 本体     | `fastapi[standard]` | FastAPI 本体。Uvicorn(サーバー)・httpx(TestClient が使用)・`fastapi` コマンドも含む |
| 本体     | `pydantic-settings` | `.env` と環境変数から設定を読み込み、型をチェックする                                 |
| 開発のみ | `pytest`            | テスト                                                                                |
| 開発のみ | `ruff`              | リンター(問題のある書き方を指摘)・フォーマッター(書き方を自動で整える)             |
| 開発のみ | `httpx2`            | TestClient が内部で使う通信ライブラリ(従来の httpx の新版。入れないと非推奨の警告が出る) |

- 「開発のみ」のパッケージは本番サーバーでは使わない
- `uv.lock` には、インストールした **正確なバージョン** が記録される。これをコミットしておくと、別の PC や本番でも同じバージョンが入る

## 5. モジュール設計

### 5.1 `app/core/config.py`:設定クラス

#### 💡 なぜ必要?

API は Supabase の URL や Gemini のキーなど、**環境(開発・本番)によって変わる値** を使う。これをコードに直接書くと、次の問題が起きる。

- 本番に切り替えるたびに、コードを書き換える必要がある
- キーが GitHub に公開されてしまう

そこで値は `.env`(本番では Render の管理画面)に置き、**設定クラスが1か所でまとめて読み込む**。
さらに型や必須のチェックもすることで、「キーの入れ忘れ」に **起動した瞬間に気づける** ようにする。気づくのが遅れると、ユーザーがチャットを送った瞬間に初めてエラーになる、という分かりにくい不具合になる。

#### 読み込みの流れ

```
OS の環境変数(本番:Render の管理画面)… 両方にある項目はこちらが優先
.env ファイル(ローカル開発用)
   │
   ▼
Settings クラス(型・必須チェック)
   ├ すべて正しい → ✅ アプリが起動する
   └ 必須項目が空・型が違う → ❌ 起動エラー(原因の項目名を表示)
```

#### クラスの構成

```
BaseSettings(pydantic-settings が用意しているクラス)
   ▲ 継承
Settings
   ├ フィールド:supabase_url など 11 項目(下の「フィールド一覧」)
   └ プロパティ:cors_origins → list[str]
```

#### 仕様

- 環境変数と `apps/api/.env` から読み込む。両方にある場合は環境変数を優先する(pydantic-settings の標準動作)
- 環境変数名は大文字、フィールド名は小文字で対応させる(例:`SUPABASE_URL` → `supabase_url`)
- `.env` に知らない項目があっても無視する
- 必須項目が未設定・空文字の場合は、起動時にエラーにする

#### フィールド一覧

| フィールド                       | 型    | 必須 | 初期値                    | 制約       |
| -------------------------------- | ----- | ---- | ------------------------- | ---------- |
| `supabase_url`                   | `str` | ○    | —                         | 空文字不可 |
| `supabase_secret_key`            | `str` | ○    | —                         | 空文字不可 |
| `database_url`                   | `str` | ○    | —                         | 空文字不可 |
| `supabase_storage_bucket`        | `str` |      | `"post-images"`           |            |
| `gemini_api_key`                 | `str` | ○    | —                         | 空文字不可 |
| `gemini_model`                   | `str` |      | `"gemini-3.5-flash-lite"` |            |
| `rate_limit_per_user_per_minute` | `int` |      | `10`                      | 1 以上     |
| `rate_limit_per_user_per_day`    | `int` |      | `30`                      | 1 以上     |
| `rate_limit_global_per_minute`   | `int` |      | `12`                      | 1 以上     |
| `rate_limit_global_per_day`      | `int` |      | `400`                     | 1 以上     |
| `cors_allow_origins`             | `str` |      | `"http://localhost:3000"` |            |

- 4.1 の時点で使うのは `cors_allow_origins` だけだが、`.env.example` の全項目をここで定義しておく(設定は1か所に集めて、「どこで定義したっけ?」をなくす)

#### プロパティ・関数

| 名前             | 種類       | 戻り値      | 仕様                                                                                  |
| ---------------- | ---------- | ----------- | ------------------------------------------------------------------------------------- |
| `cors_origins`   | プロパティ | `list[str]` | `cors_allow_origins` をカンマで分割し、前後の空白を除き、空の要素を除いたリストを返す |
| `get_settings()` | 関数       | `Settings`  | `Settings` を生成して返す。2回目以降は1回目に作ったものを返す(キャッシュ)           |

例:`"http://localhost:3000, https://example.vercel.app,"` → `["http://localhost:3000", "https://example.vercel.app"]`

- **なぜ文字列で持って、使うときにリストにするのか?** 環境変数は必ず「文字列」で渡される。`.env` に書きやすいカンマ区切りの文字列で受け取り、使うときにリストに変換するのが一番シンプル
- **なぜキャッシュするのか?** 設定はアプリの実行中に変わらない。呼ばれるたびに `.env` を読み直すのは無駄なので、1回だけ読んで使い回す
- 後の WBS で、このファイルに次の 2 つが追加される:`SettingsDep`(4.2。依存関数で設定を受け取るための別名)、`sqlalchemy_database_url`(4.3。DB 接続用の接続文字列)

#### 🔧 実装のヒント

| やりたいこと                           | 使うもの                                                                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------- |
| `.env` から読み込む・知らない項目は無視 | クラスの中に `model_config = SettingsConfigDict(...)` を書く。`env_file` と `extra` を指定する |
| 必須にする                             | 初期値を書かずに `フィールド名: 型` だけを書く                                               |
| 空文字不可・1 以上                     | `Field(min_length=1)`、`Field(default=10, ge=1)` のように `Field` で制約を付ける             |
| `cors_origins`                         | メソッドに `@property` を付ける                                                              |
| キャッシュ                             | `get_settings()` に `@functools.lru_cache` を付ける                                          |

`cors_origins` の処理の組み立て:

```
1. cors_allow_origins を "," で分割する        → ["http://a.com", " http://b.com", ""]
2. 各要素の前後の空白を取り除く                  → ["http://a.com", "http://b.com", ""]
3. 空文字の要素を除く                            → ["http://a.com", "http://b.com"]
   (2 と 3 はリスト内包表記で1行にまとめられる)
```

> ⚠️ **つまずきポイント**:`.env` に `GEMINI_API_KEY=` と値が空の行があると、「未設定」ではなく「空文字が設定された」扱いになる。`min_length=1` を付けないと、空のままチェックを通ってしまう。

### 5.2 `app/health/`:ヘルスチェック(`router.py`・`schemas.py`)

#### 💡 なぜ必要?

「API サーバーが起動していて、リクエストに応答できるか」を確かめるための、**一番シンプルな API**。次の用途で使う。

- **開発中**:サーバーがちゃんと起動したかを、すぐ確認できる
- **本番**:Render のスリープ対策として、外部から定期的にアクセスする(要件定義書 4.4)
- **Render の監視**:Render が「このサービスは正常か」を判定するのに使える

```
呼び出し元(ブラウザ / 定期実行)
   │ GET /health
   ▼
FastAPI …… DB や Gemini には接続しない
   │ 200 {"status": "ok"}
   ▼
呼び出し元
```

#### 仕様

- `router.py`:`APIRouter` を作り、`GET /health` を定義する(タグ:`health`)
- `schemas.py`:応答の形を Pydantic モデル `HealthResponse` で定義する(入出力の形は `schemas.py` に置くルール。[バックエンド構成](../../バックエンド構成.md) 3章)

| モデル           | フィールド | 型              |
| ---------------- | ---------- | --------------- |
| `HealthResponse` | `status`   | `Literal["ok"]` |

- 認証は不要
- **DB などの外部サービスには接続しない**。スリープ対策で数分おきに呼ばれるため、DB に接続すると負荷と無料枠の消費が増えてしまう
- **なぜ辞書(`{"status": "ok"}`)を返すだけにせず、モデルを作るのか?** モデルにすると、応答の形が API ドキュメント(`/docs`)に自動で載る。4.7 ではこの情報からフロントエンド用の TypeScript の型を自動生成するので、「応答は必ずモデルで定義する」というルールにしておく

#### 🔧 実装のヒント

| やりたいこと        | 使うもの                                                                      |
| ------------------- | ----------------------------------------------------------------------------- |
| ルーターを作る      | `router = APIRouter(tags=["health"])`                                         |
| エンドポイント定義  | `@router.get("/health", response_model=HealthResponse)` を関数に付ける        |
| 応答モデル          | `pydantic.BaseModel` を継承したクラス。`Literal` は `typing` から読み込む     |

### 5.3 `app/main.py`:アプリ本体

#### 💡 なぜ必要?

`core/config.py` や `health/router.py` は「部品」。`main.py` はそれらを **組み立てて1つのアプリにする場所**。起動コマンド(`fastapi dev app/main.py`)は、このファイルを起点に動く。

#### 処理の流れ

```
① get_settings() …… 設定を読む
   ↓
② FastAPI(...) ……… アプリを作る
   ↓
③ CORSMiddleware を追加
   ↓
④ health ルーターを登録
   ↓
起動完了
```

- ② は `FastAPI(title="jelgram API", version="0.1.0")`

#### 🔧 実装のヒント

| やりたいこと     | 使うもの                                                           |
| ---------------- | ------------------------------------------------------------------ |
| CORS を追加      | `app.add_middleware(CORSMiddleware, allow_origins=..., ...)`       |
| ルーターを登録   | `from app.health.router import router as health_router` → `app.include_router(health_router)` |
| 読み込み         | `from fastapi.middleware.cors import CORSMiddleware`               |

- 起動コマンドは `app/main.py` の中の **`app` という名前の変数** を探す。変数名は `app` にする

### 5.4 CORS 設定

#### 💡 なぜ必要?

ブラウザには **「今開いているサイトと違うオリジンの API は、許可がない限り使わせない」** という安全のためのルールがある(同一オリジンポリシー)。悪意のあるサイトが、ユーザーのブラウザを使って勝手に別のサイトの API を呼ぶのを防ぐためのもの。

jelgram では、画面(`http://localhost:3000`)と API(`http://localhost:8000`)の **ポートが違う = オリジンが違う** ので、何もしないとブラウザが API の結果をブロックする。
そこで API 側から「このオリジンからの呼び出しは許可します」と伝える。これが **CORS**(Cross-Origin Resource Sharing)。

#### ブラウザと API のやり取り

```
① 許可されたオリジン(localhost:3000 の画面)から呼び出す

   ブラウザ → FastAPI:OPTIONS /posts(事前確認 = プリフライト)
                        Origin: http://localhost:3000
   ブラウザ ← FastAPI:200 + Access-Control-Allow-Origin: http://localhost:3000(「いいよ」)
   ブラウザ → FastAPI:GET /posts(本番のリクエスト)
   ブラウザ ← FastAPI:200 データ
   ✅ 画面でデータを使える

② 許可されていないオリジン(evil.example.com の画面)から呼び出す

   ブラウザ → FastAPI:GET /posts
                        Origin: http://evil.example.com
   ブラウザ ← FastAPI:応答(Access-Control-Allow-Origin なし)
   ❌ ブラウザが結果を画面に渡さずブロック
```

- **プリフライト**:`Authorization` ヘッダーを付けるなど、少し特別なリクエストを送る前に、ブラウザが自動で送る「事前確認」のリクエスト(`OPTIONS`)
- CORS は **ブラウザが守るルール**。curl などブラウザ以外からの呼び出しは止められない。API 自体を守るのは 4.2 の認証の役目

#### 設定値

| 設定項目            | 値                              | 理由                                                                  |
| ------------------- | ------------------------------- | --------------------------------------------------------------------- |
| `allow_origins`     | `settings.cors_origins`         | 開発は `http://localhost:3000`、本番は Vercel の URL(環境変数で切替) |
| `allow_methods`     | `GET`, `POST`, `DELETE`         | 9章の API で使うメソッドだけを許可する(必要最小限にする)            |
| `allow_headers`     | `Authorization`, `Content-Type` | JWT(4.2)と JSON の送信に必要なものだけを許可する                    |
| `allow_credentials` | `False`                         | 認証は Cookie ではなく `Authorization` ヘッダーで行うため不要         |

- **なぜ `allow_origins=["*"]`(全部許可)にしないのか?** 動かすだけなら楽だが、どのサイトからでも API を呼べる状態になる。「必要なものだけ許可する」がセキュリティの基本

## 6. API 仕様

### `GET /health`

FastAPI が自動で作る API 仕様書(OpenAPI)と同じ YAML 形式で書く。製造後に `http://localhost:8000/openapi.json` を開くと、ほぼ同じ内容が JSON で出力される。

```yaml
/health:
  get:
    summary: ヘルスチェック
    tags: [health]
    security: []            # 認証不要
    requestBody: なし
    responses:
      "200":
        description: API が動いている
        content:
          application/json:
            schema: HealthResponse   # { status: "ok" }
            example:
              status: ok
```

- 用途:動作確認、スリープ対策の定期実行(要件定義書 4.4)

## 7. テスト設計(pytest)

### 💡 なぜ必要?

打鍵(手で動かして確認)だけだと、**後で別の機能を作ったときに、前に作った機能が壊れていないか** を、毎回すべて手で確かめ直す必要がある。
自動テストを書いておけば、`uv run pytest` の1コマンドで、何度でも数秒で確認できる。機能が増えるほど効果が大きくなる。

### 7.1 テストの仕組み

```
tests/conftest.py(テストの準備)
   ① ダミーの環境変数を設定 …… 本物のキーを使わないため
      ↓
   ② app.main を import ………… ここで設定が読まれる
      ↓
   ③ TestClient(app) を用意 …… fixture「client」として渡す
      ↓
tests/test_health.py(client.get("/health") など)
      ↓ 実際のサーバーを起動せずに呼び出す
FastAPI アプリ(メモリ上で動く)
```

- **TestClient**:サーバーを起動しなくても、プログラムの中から API を呼び出せる道具。速くて、ポートの競合も起きない
- テストがローカルの `.env`(本物のキー)に依存しないよう、ダミー値を環境変数に設定してから `app.main` を読み込む。環境変数は `.env` より優先されるので、ダミー値が使われる
  - 設定する項目:必須項目(`SUPABASE_URL`・`SUPABASE_SECRET_KEY`・`DATABASE_URL`・`GEMINI_API_KEY`)と `CORS_ALLOW_ORIGINS=http://localhost:3000`

#### 🔧 実装のヒント

| やりたいこと                   | 使うもの                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| 環境変数を設定する             | `os.environ["キー"] = "値"` を、`from app.main import app` より **前** に書く                |
| fixture を作る                 | 関数に `@pytest.fixture` を付けて `TestClient(app)` を返す。テスト関数の引数名に `client` と書くと受け取れる |
| `.env` を読まずに Settings を作る | `Settings(_env_file=None, supabase_url="...", ...)` のように `_env_file=None` を渡す          |
| エラーになることをテストする   | `with pytest.raises(ValidationError):` の中で `Settings(...)` を作る                          |
| 応答ヘッダーを確認する         | `response.headers` は辞書のように使える(`"キー" in response.headers` など)                  |

> ⚠️ **つまずきポイント**:`app.main` は読み込まれた瞬間に設定を読む。環境変数の設定を `import` より後に書くと、ダミー値ではなく `.env` の値(または未設定エラー)になる。Ruff に「import はファイルの先頭に書くべき」(E402)と指摘されるが、この場合は意図的なので、その行の末尾に `# noqa: E402` を付けて指摘を止める。

## 8. 打鍵テスト項目

### 💡 なぜ必要?

自動テストは「決めた条件」しか確認しない。実際に起動して、**人の目で使ってみて初めて気づくこと**(起動時のログが分かりにくい、ドキュメント画面の表示がおかしい等)を確認する。

| No.  | 確認内容                     | 期待結果                                                               |
| ---- | ---------------------------- | ---------------------------------------------------------------------- |
| K-01 | 起動できる                   | エラーなく起動し、`http://127.0.0.1:8000` で待ち受けるログが出る       |
| K-02 | ヘルスチェック               | ブラウザで `/health` を開くと `{"status":"ok"}` が表示される           |
| K-03 | API ドキュメント画面         | `/docs` が表示され、`GET /health` を画面から実行すると `200` が返る   |
| K-04 | 自動再起動                   | ファイルを保存すると自動で再起動し、K-02 が引き続き成功する            |
| K-05 | 設定漏れを起動時に検出できる | 必須項目が空だと起動時にエラーになり、原因の項目名が分かる             |

具体的な操作手順と結果の記入欄は [マニュアル](マニュアル.md) にある。
