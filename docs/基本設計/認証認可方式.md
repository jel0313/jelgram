# 認証・認可方式(基本設計)

## 認証(だれか)

ログインそのもの(Google ログイン・パスワード・リフレッシュトークン・メール確認)は **Supabase Auth** が行う。
FastAPI は、Supabase が発行した JWT を検証するだけ。

```
ブラウザ ─ログイン→ Supabase Auth ─JWT(ES256)→ ブラウザ
ブラウザ ─Authorization: Bearer <JWT>→ FastAPI
   get_current_user(auth/dependencies.py)
     ① 署名:Supabase の公開鍵(JWKS)で検証。alg は ES256 だけ許可
     ② 中身:exp(期限)・aud=authenticated・iss=Supabase の URL
     ③ 失効:session_id が Redis の失効リストにないか(ログアウト済みなら 401)
     ④ 状態:profiles.status が active か(凍結 403・退会 401)、role を読む
   → CurrentUser(id・email・role)
```

| カリキュラム | この アプリでの担当 |
|---|---|
| 6-1 登録・パスワードのハッシュ化 | Supabase Auth(bcrypt)。自前の実装は練習ブランチで学ぶ |
| 6-2 ログイン・JWT 発行 | Supabase Auth |
| 6-3 get_current_user | FastAPI(上の ①〜④) |
| 6-4 リフレッシュトークン | Supabase Auth(supabase-js が自動で更新) |
| 6-5 ログアウト・失効 | Supabase(リフレッシュトークン)+ FastAPI(アクセストークンを期限まで失効リストへ) |
| 6-6・6-7 パスワードリセット・メール確認 | Supabase Auth |
| 8-4 ログイン試行回数の制限 | Supabase Auth のレート制限 |

💡 なぜ自前で作らない?:パスワードの保管・リセット・メール確認は、少しの漏れが大事故になる。実績のある認証サービスに任せ、API は「渡されたトークンを正しく検証する」ことに集中するのが現場の主流。

## 認可(何をしてよいか)

| ルール | 実装 |
|---|---|
| ログイン必須 | 全エンドポイントで `CurrentUserDep` |
| 自分の投稿・コメントだけ編集・削除(7-1) | service で `user_id` を比較 → 403 |
| 投稿者は自分の投稿のコメントを削除できる(7-2) | comments/service.py |
| 非公開アカウント(7-3) | SQL 条件 `can_view_content_of()`(core/visibility.py) |
| ブロック(7-4) | SQL 条件 `not_blocked()`。どちら向きでも見えない |
| 管理者だけの操作(7-5) | `require_role("admin")` → `AdminUserDep` |
| 他人の ID を指定しても取れない(7-6) | 取得・更新の SQL に必ず `user_id = :ログイン中のユーザー` を入れる |

### 「見えない」と「権限がない」の返し方

| 状況 | 返すもの | 理由 |
|---|---|---|
| ない・非公開・ブロックで見えない | 404 | 存在するかどうかを推測させない |
| 見えるが、自分のものではない | 403 | 画面で「編集できません」と出せるように |

## トークンの置き場所(8-9)

トークンは Cookie ではなく `Authorization` ヘッダーで送る。ブラウザが自動で付けないので、CSRF(他サイトからの勝手な送信)は起きない。
もし将来 HttpOnly Cookie にするなら、SameSite=Lax + CSRF トークン(ダブルサブミット)を足す。
