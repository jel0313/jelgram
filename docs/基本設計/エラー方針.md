# エラー方針(基本設計)

## 形をそろえる(5-3)

どのエラーも同じ形で返す。画面は `message` をそのまま表示し、分岐は `code` で行う。

```yaml
code: post_version_conflict
message: ほかの画面で更新されています。読み込み直してから編集してください
details: {your_version: 1}
```

## 流れ

```
service が例外を raise(例:PostNotFoundError)
   ↓
core/error_handlers.py が受け取る
   ├ AppError とその子 ………… status・code・message をそのまま返す
   ├ RequestValidationError … 422。項目と理由だけ(入力値は返さない)
   ├ Starlette の HTTPException … 存在しない URL(404)・メソッド違い(405)
   └ それ以外(バグ)………… RequestContextMiddleware が 500 にする
                                  中身はログにだけ。応答には request_id だけ
```

## ステータスコードの使い分け(1-6)

| コード | いつ | 例(code) |
|---|---|---|
| 200 | 取得・更新の成功 | |
| 201 | 作成の成功 | 投稿・コメント・画像 |
| 204 | 成功・返す中身なし | 削除・既読・ログアウト |
| 400 | 業務ルール違反 | content_not_allowed・media_not_usable・カーソルが壊れている |
| 401 | 未認証・トークンが無効 | unauthorized・invalid_token |
| 403 | 権限がない | not_post_owner・account_suspended・comments_disabled |
| 404 | ない・見る権限がない | post_not_found・user_not_found |
| 409 | 競合 | post_version_conflict・username_taken・report_already_resolved |
| 413 | 大きすぎる | payload_too_large・image_too_large |
| 415 | 形式が違う | unsupported_image |
| 422 | 入力の形が違う | validation_error・idempotency_key_reused |
| 429 | 回数の上限 | rate_limited・chat_rate_limited(Retry-After ヘッダー付き) |
| 503 | 外部サービスが落ちている | ai_unavailable・storage_unavailable |

💡 なぜ 400 と 422 を分ける?:422 は「JSON の形が違う」(画面のバグ)、400 は「形は正しいが業務ルールで断る」(利用者に伝える)。

## ログに出すもの・出さないもの(15-5)

| 出す | 出さない(伏せる) |
|---|---|
| request_id・パス・ステータス・処理時間 | トークン・パスワード・API キー |
| エラーの種類とスタックトレース(ログだけ) | メールアドレス(個人情報) |
| 監査ログ(誰が・何を) | 422 の入力値 |
