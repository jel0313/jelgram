# 要件定義書:AI常駐型SNS(Grok風チャットアシスタント)

## 1. 概要

Instagram/X(旧Twitter)のようなSNS上に、Grokのような「常駐AIチャット」を組み込んだミニマムアプリ。
タイムライン上の投稿について、AIに質問したり解説してもらったりできる体験を提供する。

## 2. コンセプト

- 疑似タイムライン(投稿一覧)を表示
- 画面に常駐するAIチャットに、投稿について質問したり雑談したりできる
- AIキャラクターは「辛口だけど愛のある」トーン(Grok的立ち位置)

## 3. 機能要件

### 3.1 認証機能

- Supabase Auth による Google ログイン
- **全機能ログイン必須**(タイムライン閲覧・投稿・AIチャットのいずれも未ログインでは利用不可)
- 未ログイン時はログイン画面のみ表示し、ログイン後にタイムラインへ遷移
- 初回ログイン時に `profiles` レコードを作成(表示名・アイコンは Google アカウントの情報を初期値とする)
- ログアウト機能
- 表示名の変更・アカウント削除は MVP 対象外

### 3.2 タイムライン機能

- 投稿一覧の表示(投稿者の表示名・アイコン、本文、画像、いいね数、投稿日時)
- 投稿の新規作成(テキスト+画像)。投稿者はログインユーザーに紐づく
- 画像アップロード(Supabase Storageへ直接アップロード)
- いいね機能
  - 1ユーザーにつき1投稿1回まで。いいね済みの投稿で再度押すと取り消し
  - 自分がいいね済みかどうかをアイコンの状態で表示
  - 自分の投稿にもいいね可能

### 3.3 AIチャット機能

- 画面常駐のチャットUI
- ユーザーの自由入力に対してAIが応答
- 「この投稿について」ボタンから、特定の投稿をコンテキストに含めて質問可能
- 会話履歴の保持(DBに保存、ユーザー × セッション単位。「新しい会話」でセッションを切り替え)
- AIキャラクター性をシステムプロンプトで制御(詳細は 3.5)
- レート制限超過時は、キャラクターの口調で「使いすぎ」を伝えるメッセージを表示

### 3.4 画像アップロード機能

- Supabase Storageへの直接アップロード(署名付きURL方式)
- 1枚あたりの上限:**5MB**
- 許可する形式:**JPEG / PNG / WebP / GIF**
- フロントエンドでのバリデーション(形式・サイズ)に加え、Storage バケットの設定でも同じ上限・形式を強制する(フロントエンドのチェックを回避されても上限を超えるファイルは保存されない)
- バケット `post-images` は公開バケット(画像は公開URLで表示)。ブラウザからの直接アップロードは禁止し、FastAPI が発行する署名付きURL経由のみとする
- 将来的な拡張:署名付きURL発行時にもファイルサイズ/Content-Type を確認するバックエンド側ガード

### 3.5 AIキャラクター設定

**方向性**:辛口ツッコミ系。皮肉まじりだが最後は建設的で、ユーザーを突き放さない。

| 項目       | 方針                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 口調       | タメ口。軽いツッコミ・皮肉を交える                                       |
| 回答の長さ | 短め(3〜5文程度)。長い解説を求められた場合のみ詳しく                   |
| スタンス   | 本音でズバッと言うが、最後に一言フォローや具体的な提案を添える           |
| 禁止事項   | 人格攻撃、差別的表現、下品な表現、投稿者個人への誹謗中傷                 |
| 不明な場合 | 知ったかぶりをせず「知らん」と正直に言う                                 |
| 投稿言及時 | 投稿内容をネタにツッコんでよいが、投稿者本人を貶めない                   |

**システムプロンプト(初版ドラフト)**:

```
あなたはSNS「jelgram」に常駐するAIアシスタントです。
辛口だけど愛のあるツッコミ役として、ユーザーと会話してください。

# 口調
- タメ口で話す。敬語は使わない
- 軽いツッコミや皮肉を交えてよいが、最後は必ず建設的な一言や提案で締める
- 回答は3〜5文程度に収める。詳しく説明を求められたときだけ長くしてよい

# 禁止事項
- 人格攻撃、差別的な表現、下品な表現
- 投稿者本人を貶める発言(ツッコむのは投稿の内容に対してのみ)
- 分からないことを断定すること。分からなければ「知らん」と正直に言う

# 投稿について聞かれた場合
- 以下の <post> に投稿内容が与えられる。その内容を踏まえて答える
```

※ プロンプト本文は実装・試用しながら調整する前提。バックエンドのコード内で一元管理する。

## 4. 非機能要件

- 個人開発・検証レベルのスケールを想定(大規模アクセスは非対象)
- **期限なく無料で運用できること**を最優先(AWSのような12ヶ月限定の無料枠は避ける)
- 独自ドメインは使用しない(`*.vercel.app` / `*.onrender.com` を利用。HTTPSは各サービス標準で対応)

### 4.1 認証・認可

- フロントエンドは Supabase Auth のセッションから取得したアクセストークン(JWT)を `Authorization: Bearer` ヘッダーで FastAPI に送信
- FastAPI は全エンドポイントで JWT を検証し、ユーザーIDを特定する(未認証は 401)

### 4.2 レート制限

Gemini API 無料枠の急激な消費を防ぐため、`POST /chat` に対して FastAPI 側で制限をかける。

| 種別             | 上限(初期値)                                         | 超過時 |
| ---------------- | ------------------------------------------------------ | ------ |
| ユーザーごと(分) | 10回 / 分                                              | 429    |
| ユーザーごと(日) | 30回 / 日                                              | 429    |
| アプリ全体(分)   | 12回 / 分(無料枠 15回/分 の8割)                      | 429    |
| アプリ全体(日)   | 400回 / 日(無料枠 500回/日 の8割)                    | 429    |

- 無料枠の値は `gemini-3.5-flash-lite` の開発用プロジェクトで確認した実際の値(2026-09-28 時点:15回/分・500回/日)
- Gemini の上限はプロジェクト全体にかかるため、ユーザーごとの上限だけでは複数ユーザーの同時利用で超過しうる。アプリ全体にも分・日の両方で上限を設ける

- **実装方式**:DB ベース。`chat_messages` の `role = 'user'` のレコードを、ユーザーID・時間窓で集計して判定する(専用テーブルは設けない)
- DB に記録するため、Render のスリープ・再起動でカウントがリセットされない
- 上限値は環境変数で変更可能にする
- 日次の区切り
  - ユーザーごと:日本時間(JST)0時
  - アプリ全体:太平洋時間 0時(日本時間 16時 or 17時)。Gemini API の日次クォータのリセット時刻に合わせる
- Gemini 側の上限到達(API が 429 を返した場合)も、アプリの 429 と同様にキャラクターの口調で案内する

### 4.3 使用AIモデル

- **基本は Gemini Flash-Lite 系**(無料枠 15回/分・500回/日)。辛口の短い返答が中心のため性能は十分
- 採用モデル:**`gemini-3.5-flash-lite`**(2026-09-28 時点で Flash-Lite 系の最新の安定版。システムプロンプトでの応答を確認済み)
  - `gemini-flash-lite-latest` のような別名は、中身のモデルが予告なく切り替わるため使わない
- モデル名は環境変数で切り替え可能にし、必要に応じて Flash 系に変更できるようにする
- Flash 系の無料枠は約20回/日と少ないため、切り替え時はアプリ全体の上限(4.2)も合わせて下げること
- 無料枠の値は変動するため、採用時・切り替え時に [AI Studio のレート制限画面](https://aistudio.google.com/rate-limit) で実際の値を確認する(上記の回数は2026年9月時点の目安)

### 4.4 Render無料プランのスリープ対策

- 一定時間アクセスがないとスリープし、次回アクセス時に数十秒の起動待ちが発生する
- **MVPの方針**:許容する。フロントエンドで起動待ち中であることが分かるローディング表示を出す
- 体験上許容できない場合の対策案:外部の定期実行(GitHub Actions の cron 等)で14分間隔程度でヘルスチェックを叩きスリープを防ぐ(Render 無料枠の月750時間内に収まる)

## 5. 技術スタック

| レイヤー       | 技術                               | ホスティング               | 無料枠の性質                              |
| -------------- | ---------------------------------- | -------------------------- | ----------------------------------------- |
| フロントエンド | Next.js / Tailwind CSS / shadcn/ui | Vercel                     | 個人利用なら期限なく無料                  |
| バックエンド   | Python / FastAPI                   | Render(無料プラン)         | 期限なく無料(ただし無操作でスリープ)      |
| データベース   | PostgreSQL                         | Supabase                   | 期限なく無料(容量等に制限あり)            |
| 画像ストレージ | Supabase Storage                   | Supabase(DBと同一サービス) | 期限なく無料(容量制限あり)                |
| 認証           | Supabase Auth(Googleログイン)      | Supabase(DBと同一サービス) | 期限なく無料(MAU上限あり)                 |
| AI             | Google Gemini API(Flash-Lite 系)   | —                          | 無料枠あり(リクエスト数/トークン数に上限) |
| デプロイ/CI    | GitHub連携による自動デプロイ       | Vercel / Render            | 無料                                      |

**方針転換の理由**:当初はAWS(EC2/RDS/S3)で統一する案だったが、AWS無料枠は「アカウント作成から12ヶ月間」限定で、以降は課金が発生する。「とにかくずっと無料で使いたい」という要望に合わせ、期限のない無料枠を持つVercel・Render・Supabaseの組み合わせに変更。

**認証に Supabase Auth を選んだ理由**:Auth.js(NextAuth)はセッションが Next.js 側に閉じるため、別サーバーの FastAPI で認証するには追加の仕組みが必要になる。Supabase Auth は既に利用する Supabase に含まれ、発行される JWT を FastAPI で検証するだけで済むため、追加サービスなしで構成がシンプルになる。

### 5.1 開発ツール・言語バージョン

| 項目                     | 採用                                         | 理由                                                        |
| ------------------------ | -------------------------------------------- | ----------------------------------------------------------- |
| Node.js                  | 24 系(LTS)                                 | 長期サポート版で安定している。Vercel でも利用可能           |
| Node.js のバージョン管理 | fnm                                          | `.node-version` のあるディレクトリで自動的に切り替わる      |
| JS のパッケージ管理      | pnpm                                         | 高速でディスク使用量が少ない                                |
| Python                   | 3.13                                         | Render で利用可能な安定版                                   |
| Python のパッケージ管理  | uv                                           | 高速で、ロックファイルによる再現性が高い。Render でも使える |
| DB へのアクセス方法      | SQLAlchemy + psycopg(PostgreSQL に直接接続) | 集計(レート制限・いいね数)を SQL で柔軟に書ける           |
| UI コンポーネント        | shadcn/ui                                    | Tailwind CSS ベースで、コンポーネントのコードを自分で編集できる |
| バックエンドのテスト     | pytest                                       | Python の標準的なテストツール。FastAPI の TestClient と組み合わせて API を検証できる |
| フロントエンドのテスト   | Vitest + React Testing Library               | 高速で設定が少なく、Next.js(TypeScript)と相性が良い      |
| Python のリンター・フォーマッター | Ruff                                 | 高速で、コードの書き方の統一と問題の検出を1つのツールで行える |

- Python の仮想環境はプロジェクトごとに uv で作成する(`apps/api/.venv`)。conda・pyenv の環境は使わない

## 6. システム構成

```
[GitHub] --push--> 自動デプロイ
     ├─→ [Vercel] Next.js(フロントエンド)   ← apps/web
     └─→ [Render] FastAPI(バックエンドAPI, Uvicorn) ← apps/api
                        ↓
                 [Supabase PostgreSQL]
                        ↓
                 [Supabase Storage] ← 画像ファイル

[ブラウザ] --Googleログイン--> [Supabase Auth] --JWT発行
   │
   ├─ JWT付きでAPIリクエスト --> [FastAPI] (JWTを検証)
   └─ 画像を直接アップロード --> [Supabase Storage]
        ↑ 署名付きURLはFastAPI経由で取得
```

- Vercel、Renderともに GitHub と連携し、push するだけで自動デプロイ
- Next.js(Vercel)から FastAPI(Render)へAPIリクエスト、FastAPIからSupabase(DB/Storage)へアクセスする構成
- サーバー管理(Nginx設定、SSH配線など)が不要になり、AWS EC2構成より運用がシンプル

## 7. リポジトリ構成・開発環境

### 7.1 リポジトリ構成

**モノレポ**(1リポジトリにフロントエンド・バックエンドを同居)

```
jelgram/
├── apps/
│   ├── web/        # Next.js(Vercel の Root Directory に指定)
│   └── api/        # FastAPI(Render の Root Directory に指定)
├── supabase/
│   └── migrations/ # DBスキーマ定義(SQL)
├── docs/           # 要件定義書など
└── README.md
```

- Turborepo 等のモノレポツールは導入しない(JS と Python の混在で、アプリも2つのみのため)
- Vercel / Render はそれぞれ対象ディレクトリの変更時のみデプロイされるよう設定する
- API の型は FastAPI が出力する OpenAPI スキーマからフロントエンド用の TypeScript 型を生成して共有する

### 7.2 環境構成

**開発(ローカル)** と **本番** の2環境に分ける。ステージング環境は設けない。

|                               | 開発                                    | 本番                       |
| ----------------------------- | --------------------------------------- | -------------------------- |
| Next.js                       | ローカル(`localhost:3000`)              | Vercel                     |
| FastAPI                       | ローカル(`localhost:8000`)              | Render                     |
| Supabase(DB・Storage・Auth)   | 開発用プロジェクト                      | 本番用プロジェクト         |
| Gemini APIキー                | 開発用 Google Cloud プロジェクトで発行  | 本番用 Google Cloud プロジェクトで発行 |
| Googleログインのリダイレクト先 | `localhost` のURLを登録                 | 本番URLを登録              |

- **分ける目的**
  - 開発中のテストデータで本番のタイムラインを汚さない
  - スキーマ変更の失敗で本番データを壊さない
  - Gemini の無料枠はプロジェクト単位のため、開発中のテストで本番の枠(4.2)を消費しない
- Supabase の無料プランはプロジェクトを2つまで作成できるため、開発用・本番用で無料枠内に収まる
- 開発用の Supabase プロジェクトは無操作が続くと一時停止されるが、管理画面から再開すればよい
- 接続先の切り替えは環境変数で行い、コードは両環境で共通とする。APIキー等を含む環境変数ファイルはリポジトリにコミットしない(項目名だけを記載した `.env.example` をコミットする)
- DB スキーマの変更は `supabase/migrations/` の SQL で管理し、開発用プロジェクトで確認してから本番用に適用する
- **ステージングを設けない理由**
  - Render 無料プランにはブランチごとのプレビュー環境がない(有料機能)
  - 個人開発では「ローカルで確認 → 本番に反映」で十分に回る
- Vercel のプレビューデプロイ(ブランチごとの確認用URL)は、裏側の API が本番の Render に接続されるため、MVP では画面の見た目の確認用途に限る

### 7.3 Docker の方針

MVP では **Docker を使用しない**。

- 本番:Vercel は Docker 非対応、Render は Python をそのまま実行できるため不要
- 開発:DB はクラウド上の開発用 Supabase プロジェクトを使うため、ローカルで動かすのは Next.js と FastAPI のみで、Docker なしでも容易に起動できる
- 環境の再現性は、Node.js・Python のバージョンを設定ファイルで固定することと、パッケージのロックファイルで確保する
- 以下の場合に導入を再検討する
  - Supabase をローカルで動かしたくなった場合(Supabase CLI のローカル環境は Docker が必須)
  - 複数人で開発するようになった場合

### 7.4 開発の進め方

機能ごとに以下の4工程を1周ずつ回す(全機能の設計をまとめて先に行うことはしない)。

| 工程       | 内容                                                                                 | 成果物                                  |
| ---------- | ------------------------------------------------------------------------------------ | --------------------------------------- |
| 詳細設計   | 機能のモジュール構成・処理・API仕様・テストケース・打鍵項目を決め、作業手順をまとめる | `docs/詳細設計_手順/<ID>_<機能名>/` の詳細設計書・マニュアル |
| 製造       | 詳細設計書に沿ってコードを書く                                                       | ソースコード                            |
| テスト     | 自動テストを書いて実行する(バックエンド:pytest、フロントエンド:Vitest)            | テストコード(すべて成功していること)  |
| 打鍵       | 実際に操作して確認する(画面ができる前の API は FastAPI の `/docs` 画面から呼び出す) | 詳細設計書の打鍵項目の結果欄            |

- 進捗は [WBS](WBS_進捗管理表.md) で工程ごとに管理する
- 製造中に設計を変えた場合は、詳細設計書も合わせて更新する
- テストの自動実行(CI)は 3次開発で導入する。それまではコミット前に手元でテストを実行する

## 8. データベース設計(案)

ユーザー情報は Supabase Auth が管理する `auth.users` を利用し、アプリ側では表示用の `profiles` を持つ。

### profiles(プロフィール)

| カラム       | 型                      | 説明                          |
| ------------ | ----------------------- | ----------------------------- |
| id           | uuid (PK, FK→auth.users) | ユーザーID                   |
| display_name | varchar                 | 表示名(初期値はGoogleの名前)  |
| avatar_url   | varchar (nullable)      | アイコン画像URL               |
| created_at   | timestamp               | 作成日時                      |

### posts(投稿)

| カラム     | 型                   | 説明                    |
| ---------- | -------------------- | ----------------------- |
| id         | serial (PK)          | 投稿ID                  |
| user_id    | uuid (FK→profiles)   | 投稿者                  |
| content    | text                 | 本文                    |
| image_url  | varchar (nullable)   | Supabase Storage画像URL |
| created_at | timestamp            | 投稿日時                |

- いいね数は `likes` テーブルから集計する(投稿側にカウント列は持たない)

### likes(いいね)

| カラム     | 型                 | 説明           |
| ---------- | ------------------ | -------------- |
| user_id    | uuid (FK→profiles) | いいねした人   |
| post_id    | integer (FK→posts) | 対象の投稿     |
| created_at | timestamp          | いいねした日時 |

- 主キーは `(user_id, post_id)` の複合キー(1人1投稿1回をDBで保証)

### chat_messages(会話履歴)

| カラム     | 型                     | 説明                                   |
| ---------- | ---------------------- | -------------------------------------- |
| id         | serial (PK)            | メッセージID                           |
| user_id    | uuid (FK→profiles)     | 会話したユーザー                       |
| session_id | varchar                | 会話セッション識別子                   |
| role       | varchar                | user / assistant                       |
| content    | text                   | メッセージ内容                         |
| post_id    | integer (nullable, FK) | 紐づく投稿(任意)                       |
| created_at | timestamp              | 送信日時(レート制限の集計にも使用)     |

- レート制限の集計用に `(user_id, created_at)` にインデックスを張る

## 9. API設計(案)

全エンドポイントで `Authorization: Bearer <Supabase JWT>` を必須とする。

| メソッド | パス             | 説明                                                   |
| -------- | ---------------- | ------------------------------------------------------ |
| GET      | /posts           | 投稿一覧取得(各投稿のいいね数・自分がいいね済みかを含む) |
| POST     | /posts           | 投稿新規作成                                           |
| POST     | /posts/{id}/like | いいねする                                             |
| DELETE   | /posts/{id}/like | いいねを取り消す                                       |
| POST     | /uploads/presign | Supabase Storage署名付きURL発行                        |
| POST     | /chat            | AIチャット応答取得(message, session_id, post_id)。レート制限対象 |
| GET      | /chat/history    | 指定セッションの会話履歴取得(自分のもののみ)          |
| GET      | /me              | ログイン中のユーザー情報取得(認証の確認用)            |
| GET      | /health          | ヘルスチェック(認証不要。スリープ対策の定期実行用)    |

- 共通エラー:401(未認証)、429(レート制限超過)

## 10. 無料枠に関する注意事項

- **Vercel**:個人(Hobby)利用なら期限なく無料。商用利用や大規模アクセスの場合は別途確認が必要
- **Render**:無料プランは期限なく利用可能だが、一定時間アクセスがないとインスタンスがスリープし、次回アクセス時に起動待ち(数十秒程度)が発生する
- **Supabase**:無料プランは期限なく利用可能。DB容量・Storage容量に上限あり(目安:DB 500MB、Storage 1GB程度、プラン内容は変動する可能性があるため利用時に要確認)。一定期間アクセスがないプロジェクトは一時停止される場合がある点にも注意
- **Supabase Auth**:無料プランでも月間アクティブユーザー(MAU)数万規模まで利用可能で、本用途では十分。Googleログインには Google Cloud Console での OAuth クライアント作成が必要(無料)
- **Gemini API**:無料枠にもリクエスト数/トークン数の上限があり、モデルごと・プロジェクトごとに適用される。日次上限は太平洋時間0時にリセット。想定外のアクセス急増時は制限に達する可能性あり(4.2 のアプリ全体上限で保護)。無料枠の値は頻繁に改定されるため AI Studio で定期的に確認する

## 12. 開発ロードマップ(MVP以降)

MVP を「1次開発」とし、継続的に機能を積み上げていく。

### 12.1 進め方の原則

- 各フェーズの終わりは、単体でリリースできる状態にする
- フェーズの順番・中身は、実際に使ってみた結果を踏まえて都度見直してよい。見直した場合は本章を更新する
- 各フェーズの着手前に、**無料枠への影響**(DB/Storage容量、Gemini の呼び出し回数、Realtime 接続数など)を確認する
- 各フェーズの着手前に、そのフェーズの詳細要件を本書に追記してから実装する
